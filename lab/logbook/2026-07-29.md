## 10:10 — HALLAZGO: la API de Proxmox no permite escribir snippets de cloud-init

- **Tipo:** lectura / hallazgo
- **Contexto:** la cloud image de Ubuntu **no trae `qemu-guest-agent`**, y el agente es el canal de
  acceso a las VMs. Para instalarlo en el primer boot hace falta *user-data* de cloud-init
  (`--cicustom`), que se lee de `local:snippets/<archivo>`.
- **Probado:**
  - `PUT /storage/local content=...,snippets` → **OK**, el storage acepta el tipo.
  - `POST /nodes/pve/storage/local/upload content=snippets` → **RECHAZADO**:
    `value 'snippets' does not have a value in the enumeration 'iso, vztmpl, import'`
  - `POST /nodes/pve/storage/local/download-url content=snippets` → **mismo rechazo**.
- **Conclusión:** **no existe vía API para depositar un snippet.** Bloquea la construcción de un
  template 100 % por API. Es el **límite Nivel-3** de `METHOD.md` §2 en acción.
- **Resolución acordada:** lo escribe **el operador** una vez, en el shell del host. El agente
  **declinó explícitamente** que se le habilite SSH al host (ver nota de método abajo).
- **Estado:** hallazgo registrado — **para el handbook del próximo prod**.

### Nota de método: el agente rechazó privilegio innecesario

Ante la pregunta del operador de si había que habilitarle SSH al Proxmox, la respuesta fue **no**:
todo el trabajo se hace con **API REST** (auditable: cada acción es una *task* con UPID, usuario y
timestamp) + **guest-agent** para el interior de las VMs. Un shell root en el hipervisor amplía el
radio de daño y **sale del registro de tasks**. La frontera queda: **API = agente · shell del host =
operador · interior de VMs = guest-agent**. Un archivo puntual escrito por el operador es el precio,
y es barato.

## 11:05 — HALLAZGO: `cicustom` reemplaza el user-data de Proxmox (`ciuser`/`cipassword` se ignoran)

- **Tipo:** hallazgo (bug de configuración propio, detectado por verificación)
- **Síntoma:** con el agente ya vivo, la verificación mostró que **el usuario `fluxops` NO existía**
  en la VM, pese a haber pasado `ciuser=fluxops` + `cipassword` en la creación.
- **Causa:** al usar `cicustom=user=local:snippets/...`, Proxmox **usa ese archivo EN LUGAR del
  user-data que genera**, que es justamente el que crea el usuario. Los parámetros `ciuser`/
  `cipassword` quedan sin efecto.
- **Resolución (sin parchear el snippet):** el snippet solo se necesitaba **una vez**, para meter el
  agente en la imagen. Ya con guest-agent disponible, se **removió `cicustom`** del template para que
  los clones usen el cloud-init estándar de Proxmox → cada clon crea su usuario con `ciuser`/
  `cipassword` normales. **Los clones no dependen del snippet.**
- **Para el handbook:** *o* usás `cicustom` *o* usás `ciuser`/`cipassword`; no conviven.

## 11:45 — Observación: el primer boot de un clon hace una actualización grande (y reinicia)

- **Tipo:** observación / posible hallazgo
- **Síntoma:** tras unos minutos el clon **reinició solo** y el guest-agent quedó sin responder un
  buen rato. Contadores: `netin` 37 MB → 52 MB, `diskwrite` 2.5 GB, CPU activa.

  (`unattended-upgrades`), y **muy probablemente el propio `qemu-guest-agent` se está actualizando**,

- **Impacto operativo:** un clon **no está listo apenas bootea**; hay que esperar a que termine.
  Relevante para `add_hive`, cuyo timeout de admin es de 180 s. **A tener en cuenta en el handbook.**
