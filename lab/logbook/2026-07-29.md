## 10:10 — FINDING: the Proxmox API does not allow writing cloud-init snippets

- **Type:** read-only / finding
- **Context:** the Ubuntu cloud image **does not ship `qemu-guest-agent`**, and the agent is the access
  channel to the VMs. Installing it on first boot needs cloud-init *user-data*
  (`--cicustom`), which is read from `local:snippets/<file>`.
- **Tried:**
  - `PUT /storage/local content=...,snippets` → **OK**, the storage accepts the type.
  - `POST /nodes/pve/storage/local/upload content=snippets` → **REJECTED**:
    `value 'snippets' does not have a value in the enumeration 'iso, vztmpl, import'`
  - `POST /nodes/pve/storage/local/download-url content=snippets` → **same rejection**.
- **Conclusion:** **there is no API way to drop a snippet.** It blocks building a
  template 100 % via the API. This is the **Level-3 limit** of `METHOD.md` §2 in action.
- **Agreed resolution:** **the operator** writes it once, in the host's shell. The agent
  **explicitly declined** SSH access to the host (see the method note below).
- **Status:** finding recorded — **for the next prod's handbook**.

### Method note: the agent turned down an unneeded privilege

When the operator asked whether to give it SSH access to the Proxmox, the answer was **no**:
all the work is done with the **REST API** (auditable: every action is a *task* with UPID, user and
timestamp) + the **guest-agent** for the inside of the VMs. A root shell on the hypervisor widens the
blast radius and **falls outside the task record**. The boundary stays: **API = agent · host shell =
operator · inside the VMs = guest-agent**. A single file written by the operator is the price,
and it is cheap.

## 11:05 — FINDING: `cicustom` replaces the Proxmox user-data (`ciuser`/`cipassword` are ignored)

- **Type:** finding (my own configuration bug, caught by a check)
- **Symptom:** with the agent already alive, the check showed that **the user `fluxops` did NOT exist**
  in the VM, even though `ciuser=fluxops` + `cipassword` were passed at creation.
- **Cause:** with `cicustom=user=local:snippets/...`, Proxmox **uses that file INSTEAD OF the
  user-data it generates**, which is exactly the one that creates the user. The `ciuser`/
  `cipassword` parameters have no effect.
- **Resolution (without patching the snippet):** the snippet was only needed **once**, to get the
  agent into the image. With the guest-agent available, **`cicustom` was removed** from the template so
  the clones use Proxmox's standard cloud-init → each clone creates its user with the normal `ciuser`/
  `cipassword`. **The clones do not depend on the snippet.**
- **For the handbook:** *either* you use `cicustom` *or* you use `ciuser`/`cipassword`; they do not coexist.

## 12:15 — A-5 CONFIRMED: the clone needs a reboot to be ready

- **Type:** finding check
- **Sequence seen on `fb-build` (110):** boot → cloud-init runs → **big automatic upgrade**
  (`netin` 37→52 MB, `diskwrite` 2.5 GB) → **spontaneous reboot** → **`qemu-guest-agent` does NOT come back**

- **State after the reboot:** cloud-init `done`, agent `active`, `ssh.socket` `active`,
  `dpkg --audit` clean, no `reboot-required`.
- **Conclusion:** **a freshly booted clone is NOT ready.** You have to wait for the upgrade to finish
  and **reboot it** before treating it as operational. It hits `add_hive` directly (+ its timeout of
  180 s). → `FINDINGS.md` **A-5** confirmed.
