## The working method changes (the operator)

With small changes each cycle took about 3 hours, and the operator asked for another way. Measured
on 0.1.105's cycle, 3 h 31 min from the operator's choice to the version's close:

| Stage | Time |
|---|---|
| The code and its own tests | 36 min |
| The review round and its fixes | 26 min |
| The full check on the Mac | 1 h 43 min |
| GitHub's CI (3 min) beside the build (23 min) | 24 min |
| Publish and deploy | 6 min |
| The gate on 8.x | 12 min |
| The docs' close | 2 min |

- The Mac's pass compiled the tests in 3.5 min and ran them in about 80 s; the rest went between one
  test binary and the next. 0.1.104's pass took 1 h 35 min the same way. GitHub runs the same check
  in 3 min.
- **The operator's choice** ([METHOD](METHOD.md) §9): a `coa/<item>` branch per change, tested by
  GitHub, with the Mac only compiling; releases of several changes that touch different binaries,
  each with its own gate, the gates in parallel. Installing binaries by hand on 8.x was weighed and
  left out: a path parallel to the product's (rule 0c), managed nodes run from dist, and it would
  save only the build and the deploy, about 30 min.
- **GitHub's cache:** capped at 10 GB per repo, it held 8.6, each branch keeping its own copy of
  about 2 GB. The Rust cache is now saved on `main` only, and every branch reads it.
- **The first branch, `coa/ci-cache`:** the cache change, and `lab/ci.py`, which waits for a
  commit's CI on any branch and prints the end of a failed step's log. On the branch the Rust cache
  came from `main` (a full match) and nothing was saved; the root workspace's job took 3.5 min, the
  IO workspace's 1 min. Integrated into `daily_onworking_coa` and deleted.
- The copies kept by `daily_merge` and `daily_onworking_coa`, and an old one of `main`, could not be
  deleted: the token lacks the permission (403). They break nothing; GitHub's Actions → Caches page
  removes them.
