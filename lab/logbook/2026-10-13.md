# 2026-10-13 — Fluxbee Cloud: decisions O5–O8 and the io.cloud package in PROD (0.1.64)

## The operator's decisions

- **The order of the Cloud track:**
  1. first the io.cloud functions;
  2. then the identity talk: one person in several companies, and parent/child tenants;
  3. then the certificate;
  4. at the end, together: what io.web is, how Archi goes out, and the blob docs.

  One track at a time: *"no quiero ir por las dos cosas a la vez"* (I don't want to go for both
  things at once).
- **O5 (a), and the same security for io.cloud and io.web:** *"si no los hay para io.cloud no los
  abriría para io.web"* (if there are none for io.cloud, I would not open them for io.web). Verified
  in the code: io.cloud does have a gap today. The edge is the trust anchor: it checks the bearer,
  strips it, and sees everything in clear text. Proposal for the io.web v2 spec: one host per node
  and SNI passthrough without opening, with mTLS from Cloud to io.cloud.
- **O6, Let's Encrypt (*"veo que es el estándar"* (I see it is the standard)):**
  - with TLS-ALPN-01 on :443, no port 80 and no DNS credentials;
  - it goes with Archi via Cloud;
  - there is nothing to do today: the Sectigo wildcard covers `hive-k3m9x7q2` until 12-Feb-2027,
    but never `archi.<id>`;
  - because of SC-081 there are no more one-year certificates: the maximum is 200 days, and 100
    from March 2027.
- **O7:** one ingress, one egress and one edge per install, each install with its own name.
- **O8:** no tenant label and no hosts per tenant, because it is already solved: opaque ids
  (`/e/<ich>`, `/public/<key>`). One Archi per install. `/t/<label>/` is withdrawn from the spec.
- **io.web:** the repo only has the beta spec, no code. It starts from zero when its turn comes.

## The Cloud team's tickets, against the code

- **They started from an old picture:** they talked about 4 operations, and there are 13.
  `docs/io-cloud-api.md` said 3, and configuration through `.env`.
- **The bug of the undecoded query** was already fixed in 0.1.50.
- **`display_name` versus `name`:** they were right, it was an error in the doc.
- **`enabled:false` on the `cloud` channel:** it is fine, it only means "not published on the
  edge".
- **My own finding (A-61):** `put_token` overwrote keys of any tenant, including the infrastructure
  ones.

## The package (0.1.64)

- **The tenant in the vault, for every caller** (the operator's request midway: *"cambiá el tema de
  incluir el TNT en el pedido al vault en todo lo que llama a eso"* (change the matter of including
  the TNT in the request to the vault, in everything that calls it)):
  - a put of someone else's key is `KEY_TAKEN`;
  - delete, rotate and roll back carry `tenant_id`.

  All the callers were reviewed: the admin HTTP, the Archi plans, the orchestrator cleanup, the
  factory reset and the teardown e2e.
- **The relay gate trap**, which had already bitten on 2026-09-28: adding actions to the Cloud
  surface took them away, over the mesh, from everyone else. They were left specifically to the
  orchestrator (the cleanup of a node) and to Archi. For Archi, `get_ilk` and `run_node` were
  already rejected.
- **"Solo ILKs humanos" (only human ILKs) is on hold:** the operator corrected that on the spot
  (*"puedo haberte dicho mal"* (I may have told you wrong)). Assigning a token to a node does not
  change the ILK, only the metadata of the secret. It goes to the identity talk.
- **What was left out:** any node on the mesh can ask the admin for any action. It was parked as
  A-62, with its cost/benefit.
- **Review:** one round. One MAJOR (the factory reset) and six minors, fixed.
