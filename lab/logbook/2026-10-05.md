## Archi (A-46): what the operator asked for

*"Archi tiene que estar publicado en el edge para que Fluxbee Cloud lo pueda mostrar como parte de
su website, además tiene que estar internamente con localhost para mantenimiento... lo demás tiene
que estar cerrado... no veo necesario ponerle login a Archi."* (Archi has to be published on the
edge so Fluxbee Cloud can show it as part of its website; it also has to be there internally, on
localhost, for maintenance... the rest has to be closed... I don't see the need to put a login on
Archi.)

### Survey (read-only, the 4 hosts)

- **Nothing filters incoming traffic.** ufw is inactive on all of them. The rules that the
  orchestrator "opens" are stored with no effect, and if someone turns ufw on, SSH and 443 get
  blocked (A-46 extended).
- **Listening on external interfaces:** the ingress SSH and Syncthing, also on the public
  interface; the egress ones, on the office network.
- **Syncthing uses public discovery, relays and NAT**, and worker1 ↔ motherbee are `dynamic` on both
  sides, so they sync thanks to discovery (A-47).
- **Archi:**
  - the packaged example, the dev `config/hive.yaml` and the docs say `0.0.0.0`;
  - the postinst does not touch a `hive.yaml` that already exists;
  - the UI builds its URLs relative to the path, so it works unchanged behind a host of its own.
- **There was already a prior design for the external part:**
  - the name `hive-k3m9x7q2` (HANDBOOK §8);
  - the FC.edge-manager, with a certificate per edge and Cloud owning the DNS (C1), which was never
    implemented;
  - the IO.web beta spec, which only models tenant apps and assumes a firewall that does not exist.

### What the operator decided

- The orchestrator declares, applies and verifies the host posture: *"el que tiene que setear todo
  lo del entorno en ese sentido es el orchestrator, como concepto al correr verificaría eso"* (the
  one that has to set up everything about the environment in that sense is the orchestrator; as a
  concept, when it runs it would verify that).
- Archi and the admin stay on loopback only. DEV moves to an SSH tunnel.
- Syncthing stops using the public infrastructure.
- The only public thing is the ingress 443.
- Cloud is trusted: *"le creemos ciegamente al cloud y el cloud resuelve con un url"* (we believe
  the cloud blindly, and the cloud solves it with a url).
- One public ID per install; PROD reuses `hive-k3m9x7q2` → `archi.hive-k3m9x7q2.fluxbee.ai`.
- The operator handles the DNS by hand (Azure); it gets automated later.
- No second domain: tenant content goes as a directory on the edge.
- The Archi app is not touched: *"lo que está de archi no lo cambies.. eso lo vemos después, cloud
  replica"* (don't change what is there for archi.. we look at that later, cloud replicates).
- IO.web will handle the artifacts (security, maybe share); it is noted, not designed.
- How the work goes: *"documentar todo este choclo y después asegurarse con un DTAP (panel)... e ir
  probando en infra"* (document this whole mess and then make sure with a DTAP (panel)... and keep
  testing on infra). In stages, never in one pass.

It all went into `docs/host-posture-and-exposure-spec-v1.md`: the current state with citations to
the code, decisions D1–D15, open items O1–O4, and a plan in 8 stages, each with its validation on
infra. The DTAP panel runs on that document.

## DTAP panel on the design → revision 2

The panel was done with agents: Development, Test, Acceptance and Production, each with an
adversarial verifier. **All 4 lenses failed it**: 75 findings, 51 confirmed and 24 partial, none
refuted. The blockers:

- **D-1:** the egress nft idiom does not replace sets or chains. A removed hive would still be
  admitted.
- **T-1:** turning off discovery depends on the stages being installed one by one. Skipping
  versions cuts off worker1.
- **T-2:** the rollback covered only the live table. A ruleset that failed came back through the
  boot file or the watchdog.
- **A-1:** the O1 default (the motherbee subnet) gave SSH to the DMZ ingress and left out the
  people on the VPN.
- **P-1:** a compromised ingress can issue and use an Archi session on its own. The edge is the
  only one that validates the Cloud bearer, and it also terminates TLS.

**Also found:**

- nftables is not a dependency;
- the posture settings do not reach the spokes (their `hive.yaml` is not re-sent);
- the address in the registry is the SSH destination, not the source IP;
- the probes reverted correct rulesets (9100 from ingress and egress);
- nothing tears down the posture (`remove_hive`, downgrade, purge);
- io.linkedhelper has a direct listener outside the edge;
- Archi has no CSRF protection and accepts any Content-Type;
- the edge routes by path on any Host;
- the brand's wildcard is in the DMZ;
- publishing goes through a single edge.

**Result:**

- Revision 2 adds all the technical points.
- The record of each finding is in `docs/audits/2026-10-05-host-posture-dtap-panel.md`.
- Two new findings outside the design: **A-48** (`remove_hive` does not revoke credentials) and
  **A-49** (an unsigned apt repo with `[trusted=yes]`).
- Operator decisions: O1–O4 before stages 1–5 (SSH sources, Archi by config, io.linkedhelper,
  isolating the ingress) and O5–O8 before 6–7.
- Next: the operator's answers, a second DTAP round on Part A, stage 1.

## The operator's answers → revision 3

1. **SSH:** OK to it never being blocked for lack of data. It ended up like this (D16):
   - with no declared sources, open to everyone except the registered hives, so the ingress cannot
     get into the motherbee or the spokes;
   - on the ingress, only through the internal interface, which the orchestrator derives from the
     route to the motherbee;
   - nobody has to configure anything.
2. **Archi:** to loopback only through configuration (D17).
3. **io.linkedhelper:** *"hay que integrar el nodo de linkedhelper para que haga el mismo camino
   que edge, pero eso dejalo postergado para el final"* (the linkedhelper node has to be integrated
   so it takes the same path as edge, but leave that postponed until the end) (D18).
4. **Ingress:** *"no la compliques, lo tiene que resolver el add_hive con ese role y el
   orchestrator... el usuario no puede hacer config complicado desde infra, si queda algo raro no
   lo hagamos ahora"* (don't complicate it; add_hive with that role and the orchestrator have to
   solve it... the user cannot do complicated config from infra; if something odd is left, let's
   not do it now) (D19). Only its automatic posture gets done. VLAN, anti-spoofing, the outbound
   filter and an edge without root stay as residuals, for after the core.

Work order (D20): *"quiero cerrar el core primero, luego conexión con fluxbee cloud y luego los
nodos de implementación"* (I want to close the core first, then the connection with fluxbee cloud,
and then the implementation nodes):

- **Core:** stages 1–5, A-48 and A-49.
- **Cloud:** stages 6–7.
- **Implementation nodes:** io.linkedhelper and the rest.

## Second DTAP round → revision 4, simplified

Round 2 was only on Part A (the core) of revision 3. **All 4 lenses failed it again**: 84 findings,
4 blockers, none refuted.

**The common cause** is the mechanisms that revision 2 had added to filter the mesh ports by the IP
of each hive, and to manage the spokes from the motherbee: source IPs, settings push, probes,
timers, quarantine. Each one brought its own failures:

- a hive that changes IP was locked out forever;
- the join was circular;
- the spokes never receive the registry;
- any orchestrator could send the push.

The Acceptance lens concluded that security needs none of them, which is the operator's *"no la
compliques"* (don't complicate it).

**Revision 4 simplifies:**

- **Rules by port and interface, according to the role.** The mesh ports are already
  authenticated, and A-48 stops removed hives in the protocol.
- **Automatic mode.** It observes for 24 h and then blocks by itself. If the rules change, it goes
  back to observing.
- **No configuration.** Only two local files, for us: break-glass and hold.
- **No probes or timers.** A rule is applied only after it runs clean in observation.
- **SSH only on the internal interface.**
- **A-48 and A-49 detailed.**

**Left for the operator:** OK to D3 and D16 (they change what the operator had accepted), and
whether anyone gets into the egress over SSH through its office IP, or into the ingress through the
public one.

**Record:** in the same audit, section "Round 2". Next is round 3, on revision 4.
