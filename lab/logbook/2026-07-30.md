## 00:20 — The full-chain `.crt` came malformed

The operator left `sslcert/fluxbee_fc.crt` with the full chain. **The chain is the right one:**

```text
*.fluxbee.ai
  └─ Sectigo Public Server Authentication CA DV R36
       └─ Sectigo Public Server Authentication Root R46
            └─ USERTrust RSA Certification Authority   (self-signed, already in the trust stores)
```

Verified: `openssl verify` → **OK** · the private key **matches** (same modulus) · the leaf is
**exactly the same** one already in production (same SHA-256 fingerprint) — so only the chain was
added; the certificate did not change.

**But the file does not parse.** On line 38, the leaf's `-----END CERTIFICATE-----` and the
intermediate's `-----BEGIN CERTIFICATE-----` are **stuck together on the same line, with no line break**,
plus mixed CRLF. With that, `openssl` reads **zero** certificates from the file.

I normalized it (CRLF→LF, split the stuck delimiters), and then all 4 show up. To serve, I used
**leaf + the 2 intermediates**, without the self-signed root: the roots are already in the trust stores,
and sending it only adds ~1.5 KB per handshake. Validated against the system CAs: **OK**.

**This opened a product finding** ([PB-2](PENDING-BUGS.md#pb-2)): `vault_put` with
`resource_type=tls` accepts any string. Had the broken file been loaded as is, the `put` would
answer `ok` and the failure would show up at the edge's next boot, with a symptom that does not mention the
vault: *"the edge does not bring up HTTPS"* — and since the edge is *fail-closed*, that means the public door
is down. It should be validated on write.

## 00:45 — Loading into the vault and **the broadcast bug, reproduced live**

Before loading, I asked the system for the exact shape of the call
(`GET /admin/actions/vault_put`) instead of assuming it — the self-documentation the operator built
gives the full schema, including the note that `metadata.owner_ilk` is rejected.

```text
POST /hives/motherbee/vault/secrets
  key      = edge_tls_fluxbee_ai
  value    = {cert: <chain of 3>, key: <private>}
  metadata = {resource_type: tls, owner_node: SY.edge@ingress1, description: ...}
  -> status: ok · changed: true · version: 2
```

The temporary files with the private key were deleted with `shred` on the motherbee and on my machine.

**And here came the interesting part.** The operator had sensed that *"el vault debería mandar un signal
broadcast"* ("the vault should send a broadcast signal"). I checked it before restarting anything, and the
result was better than a suspicion: a demonstration.

```text
vault at version 2, with the chain of 3 certs
broadcast VAULT_SECRET_CHANGED emitted
openssl s_client against the edge  ->  1 cert served      <-- version 1, the old one
```

**The edge was still serving the old certificate.** A precise diagnosis, which corrects the initial
hypothesis: *the broadcast is not missing*. `SY.vault` emits it on every `put`, and half the system consumes it
(`sy_identity`, `sy_storage`, `sy_cognition`, `sy_architect`, `sy_admin`, `io.slack`, `io.wapp`).
**`sy_edge` receives and handles it too**, origin check *fail-closed* included. The gap
was much narrower: the handler only called `resolve_secrets()`, which refreshes the **channel**
secrets — the TLS material is read only once at boot and stays frozen inside the listener.

I restarted `sy-edge`, and it was right:

```text
0 s:/CN=*.fluxbee.ai
1 s:/C=GB/O=Sectigo Limited/CN=Sectigo Public Server Authentication CA DV R36
2 s:/C=GB/O=Sectigo Limited/CN=Sectigo Public Server Authentication Root R46
```

**Strict validation from the internet** (Python `ssl`, which does **not** do AIA fetching — so the
chain stands on its own, without relying on the client's goodwill):

```text
OK — TLSv1.3, cert valid until Feb 12 23:59:59 2027 GMT
curl https://hive-k3m9x7q2.fluxbee.ai/  ->  http=404  tls_verify=0
```

The 404 is still the right answer: `SY.edge` only serves `/e/<ich>`.

> **Why this bug was dangerous as well as annoying.** The symptom is **silent and misleading**: a
> lenient client (a browser, curl with the CA cached) completes the handshake anyway by fetching the
> intermediate through AIA, and reports `tls_verify=0`. It looks fine exactly where it does not matter, and it fails on
> the strict clients — which here are exactly the ones that are going to call in: the Meta and Slack webhooks.

> **My own error, on record.** My first external measurement gave "0 certs", and I almost reported that the
> edge was down. It was **my own false negative**: I used `timeout`, which does not exist on macOS, and the
> whole command died without running `openssl`. I fixed it before drawing conclusions. Reminder:
> an "all zero" result calls for checking the tool before the system.

## 01:30 — Fix for [PB-1](PENDING-BUGS.md#pb-1), with the operator's decision

**Operator's decision:** apply the house pattern now (not blocking), and open a dedicated document
of pending bug tasks from this integrated test, to review them later. Verbatim:
*"lo correcto es que haga hot-reload pero ahora tiene que salir andando y el método patrón de la
casa no es bloqueante"* ("the right thing is for it to hot-reload, but right now it has to come out
working, and the house's standard method is not blocking").

**[`PENDING-BUGS.md`](PENDING-BUGS.md)** was created with the 8 open code tasks (today's 4 new ones
plus the 4 from the `A-*` series that were already in FINDINGS).

**The fix** (in `sy_edge.rs`) follows the contract the house already uses for vault material that
can only be consumed at startup — `exit(0)` and let systemd restart it — which is literally what
`sy.identity` and `sy.storage` do with the postgres secret (Model D' VA-J'-13). No new
mechanism was invented: the existing one was applied.

Four decisions worth writing down:

1. **It reuses the origin check `sy_edge` already had.** Only the `SY.vault@<vault_hive>` this
   edge uses can trigger the restart. Without that, any node that forges the broadcast restarts it
   in a loop.
2. **It matches by key**, departing *on purpose* from the `(resource_type, tenant_id, ilk)` guidance that
   `VaultSecretChangedPayload` documents. That guidance is for consumers that resolve *by interest*;
   the edge has **an explicit `tls_vault_key`** and looks up that exact key. The divergence is
   justified in the code comment.
3. **A `delete` does NOT restart.** Restarting without a cert is *fail-closed* → the edge is left without an
   HTTPS frontend. It would turn a mistaken call to the vault into a public outage. It keeps serving what
   it already has and shouts in the log.
4. **The decision was extracted into a pure function** (`tls_secret_change_action`) so it can be tested:
   with `process::exit` inline it could not.

**Tests:** 4 new regression tests (rotation requires a restart · delete never takes down the public door ·
other secrets do not touch it · a malformed payload is reported, not swallowed). **23/23 green** in
`sy_edge`.

**What is still pending and why:** the real hot-reload (rustls's `ResolvesServerCert` over an
`ArcSwap`, zero downtime) is the right fix and is documented in PB-1. It was not done now, by
the operator's explicit decision.

⚠️ **The fix is in the repo, NOT in the running production.** The deployed binary is the one from the previous
`.deb`. It goes into the next build. Today's production was left correct by the manual restart.

## Error analysis of the rebuild (the operator's request)

### A. My own errors → rules for the HANDBOOK

| # | What happened | Rule |
|---|---|---|
| 1 | I configured 102/103 **after** the first boot; cloud-init was already `done` and did not generate the network | **Configure the whole VM BEFORE the first start.** If it already started: `cloud-init clean` **+ a full stop/start cycle** — a `reset` is NOT enough; the cloud-init disk is not regenerated |
| 2 | I killed the pollers when the host became unreachable; the cloning went on on the server side and I left a half-built VM | **The work lives in Proxmox, not in my session.** Do not cut the watchers over a transient loss |
| 3 | I ruled out the VPN because `route -n get` said `en0` | **A VPN client filters below the routing table.** Timing correlation with a network change is worth more than the table |
| 4 | I used `POST /hives/motherbee/hives` (it does not exist) and a flat payload for egress | **Ask the system**: `GET /admin/actions/<action>` gives the route and the schema. It saved me twice |
| 5 | `set -- $spec` in loops: zsh does **not** split unquoted words | Avoid loops with word-splitting; explicit values |

### B. Real product gaps → [`PENDING-BUGS.md`](PENDING-BUGS.md)

- **[U-6](PENDING-BUGS.md#u-6) 🔴 BLOCKER for ingress/egress** — `add_hive` runs a **race**
  between the vendor push over SSH and the `fluxbee-dist-vendor` folder. The ingress's first join
  failed with `size mismatch expected=35806960 actual=22364160` (62 %, a half-written file).
  **It is a consequence of U-2**: before, SSH was the only writer of `dist/vendor`. Transient — the
  retry passed and both ends ended up exact — but the first attempt always fails.
- **[U-7](PENDING-BUGS.md#u-7)** — my bug: the watchdog looks for `fluxbee-dist-core-motherbee`, which

- **[U-9](PENDING-BUGS.md#u-9)** — unknown routes return a bare `{"error":"not_found"}`,

### C. Infrastructure

## 22:30 — 🏆 THE UPDATE CYCLE, CLOSED AND VALIDATED

With prod rebuilt on 0.1.1, the full update cycle was tested with **five chained upgrades
in production**. The three blockers of the U series are closed **with live
evidence**, not with tests.

### U-1 — the update reported success without restarting anything · VALIDATED

The ideal scenario came about by itself: the worker was running the `sy-orchestrator` from the original join (17:11)
while syncthing had already delivered the new binary to it.

```text
BEFORE  pid=4027   17:11:10   /usr/bin = 0716f1f1…   dist = 1e2726ed…   <- real delta
AFTER   pid=54775  22:25:27   exe=/usr/bin/sy-orchestrator WITHOUT "(deleted)"
                              /usr/bin = 1e2726ed… = dist               <- promoted
```

Before the fix, this would have answered `ok` with the services untouched and `exe` pointing to a
deleted inode. **The `/proc/PID/exe` assert passes.**

### U-2 — per-role dist · VALIDATED

The worker's manifest matches the motherbee's **exactly**, and the per-role manifest too
(`a9a60fb8…`), which is what makes the staleness gate work. It confirms in practice the
decision to send the **full** manifest and scope only the binaries.

### U-10 — the upgrade orphaned every runtime node · VALIDATED on the third try

| upgrade | result | what it taught |
|---|---|---|
| 0.1.2 → 0.1.3 | ❌ `failed=4` | The re-resolution by intent worked; the relaunch died on the unit name that was still loaded |
| 0.1.3 → 0.1.4 | ❌ **identical** | The sameness was the clue: `systemd_unit_exists()` appends `.service` and was being passed one that already had it → the guard exited early and **the cleanup never ran** |
| 0.1.4 → 0.1.5 | ✅ `started=4` | The four nodes repaired themselves **on their own in ~25 s**, with no intervention |

> **Method lesson.** An error that repeats **identically** after a fix almost never means
> "the fix was not enough" — it means that **it did not run**. Had it run and failed, the message
> would be different. I lost a whole cycle by not reading it that way.

### Leftovers, all closed

- **The rebind over HTTP lied twice.** First it stored the request as an inert config key
  (the route wrapped the whole body under `"config"` while the logic read at the top level).
  With that fixed, it **accepted `9.9.9`** — a version that does not exist — with `ok`. Now it validates against the
  manifest and answers `RUNTIME_NOT_AVAILABLE` at request time.
- **The SSH noise went quiet:** 0 warns verified, against one per hardened spoke per pass.
  A hive with `ssh_access=revoke` has no SSH channel *on purpose*.
- **`tenant_id`: ruled out**; it was documented. My own reading error.

### What is still open

- **[U-8]** Long operations have no queryable progress. `update category=core` returned
  `TIMEOUT` at 60 s even though **it completed** — the update restarts the target's own orchestrator,
  which is the one that had to answer. An `error` on a successful operation.
- **The `kill` → `remove_instance` order** is not documented (`NODE_ALREADY_EXISTS` if it is skipped).

### The cycle now proven

```text
small commit  →  build (~6 min, warm cache)  →  apt install  →  the system settles by itself
```

Prod ended on **0.1.5**: 4 runtime nodes active, full mesh, public HTTPS with the full
