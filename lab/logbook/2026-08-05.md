## The bug the regeneration found

**`add_egress_hive_flow` never pushed the vendor bundle.** Of the three join flows it was the
only one: worker and ingress do it. A divergence between siblings.

The consequence seen on the box: the egress never receives the syncthing binary, and since the vendor
arrives **through** syncthing, it cannot repair itself. The watchdog retries every ~5 s
forever:

```text
syncthing unhealthy; restarting  service_active=false
blob sync watchdog failed  error=vendor manifest missing ... or missing 'syncthing' component
```

I found it by pulling the thread of a `vendor: unknown` in `/versions` — an **honest** unknown, which
is only visible thanks to the U-4a fix. Fixed in `e03d2aa`, mirroring the ingress flow,
with a test that reads the source and requires all three flows to push core **and** vendor. I checked that
this test **would have failed** against the old code before trusting it.

⚠️ **The fix is NOT deployed**: prod runs 0.1.8, which still has the bug. Validating it needs
a new `.deb` and re-joining the egress.

On the way to testing what was missing, **three divergences of the same flow** showed up, chained. All
three have the same pattern: `add_egress_hive_flow` did not do something that worker and ingress did. No test
saw any of them, the `.deb` installed perfectly, and the symptom only shows up in the least exercised role.

1. **It did not push the vendor** (`e03d2aa`) → the egress never received the syncthing binary.
2. **The syncthing home was not created** when only the DIST sync needs it (`6529c85`) → the
   service started without a `WorkingDirectory` and died with `200/CHDIR` in a loop. The whole transport down.
3. **It did not link its Syncthing peer** (`72a133e`) → the motherbee's `fluxbee-dist-core-egress`
   folder listed **1 device** against 2 for worker and ingress. The egress joined fine and then
   **could never be updated, silently**: `update category=core` found its dist unchanged
   and did nothing.

**The test that counts:** the egress VM destroyed and re-created from the template, a single operator
step (the authorized_key, now documented in `template-prep.sh`), and a clean join with 0.1.11.
Result, without touching anything by hand: vendor present, home **created by the code**, `fluxbee-dist-core-egress`
with **2 devices**. Fleet at `match`.

The symmetry test now requires all **three** steps of all three flows, and I checked that it would have failed
against the old code in each case. That is what keeps a fourth one from happening.

## U-5 closed

The cross-hive forward (`eb489cb`) turned out not to be optional: without it the action was **unreachable**
— the motherbee has the API but never produces sealed generations (dpkg handles its core), and the
spokes have them but expose no API. Validated live on worker1: `dry_run` correct, a real rollback
applied (`source: core_rollback`, `rolled_back_from`, 8 units 0 failed), and **X1 confirmed**
— `/versions` marked it `core: differs` even though its `dist/core` was identical to the motherbee's.

A forwarded rollback **loses its response by construction** (it restores `sy-orchestrator` and
restarts it): it is now `FORWARD_UNKNOWN` (409, retryable) pointing at `core.installed.source`, not a
message that sends you hunting for a failure that does not exist (`5362dad`).

## The `sy-storage` startup race — fixed in the SDK

The motherbee's journal gives the diagnosis with no room for interpretation. Two forms, **six
occurrences**:

```
SY.storage vault lookup for postgres_url_ref failed; starting degraded
  error="... vault unreachable: reason=NODE_NOT_FOUND original_dst=SY.vault@motherbee"
  error="... node error: disconnected"
```

So it **was not rare**: losing the race is the normal result of restarting everything together. It is not
that the vault said "I do not have that secret" — it is that **nobody answered**, because `sy-vault` had not
yet announced itself to the router.

And there was no ordering that would help: both units are `After=network.target`, `Type=simple`.
Adding `After=sy-vault.service` would be decorative, because with `Type=simple` "started" means "the
process ran", not "it announced itself on the bus". The race would stay the same.

**Why the rescue that already existed was not enough.** It is documented as the "option C" fix: reuse
the persistent connection so that a later `VAULT_SECRET_CHANGED` brings it up. That is **push**, and
the vault's bootstrap broadcast is a **one-time event**. A storage that was not listening yet
does not get a second notice — and it stays degraded until someone restarts it by
hand. With the hive's admin plane down along with it, behind `STORAGE_NOT_READY`.

**The fix.** The **pull** is missing: keep trying until the vault is really reachable. It goes in the
SDK (`resolve_resource_awaiting_vault`), not in each binary, because — the look-at-the-siblings rule —
`sy-identity` **already retried**, and had for a while, 15 s with its own loop. Storage was the outlier. Now
both wait the same way, with a single definition of the cutoff:

- `Unreachable` / `TtlExceeded` / `Node` / `ActionTimeout` → nobody answered; retry.
- `Service` / `EmptyValue` / `InvalidVaultRef` → **there was a verdict**; no retry. A vault that
  says "that secret does not exist" will say the same on attempt 80; insisting would only delay a
  degraded start that is legitimate, and the operator has their `CONFIG_SET`.

**Push and pull together close the whole loop**, which is what matters so it does not happen again:

| when the vault arrives | who covers it |
|---|---|
| it was already up (the broadcast already went by) | the **pull** resolves on the first attempt |
| it arrives within the 60 s | the **pull** waits for it |
| it arrives after the 60 s | storage started degraded **but keeps listening** → the broadcast triggers the `exit(0)` and `Restart=always` brings it back with the secret |

That storage keeps serving the bus while degraded is not theory: it is exactly through that
path that it returned `STORAGE_NOT_READY` 70+ times.

Three tests pin down the evidence — the two **verbatim** journal errors as retryable, the
verdicts as non-retryable, and that the wait is bounded (a vault that never arrives must
end in a degraded start, not in a process hung forever).

## Live validation of the race fix — 0.1.12 and 0.1.13

The race fired **four times** during the day, and all four were absorbed on their own:

| event | error seen | outcome |
|---|---|---|
| upgrade 0.1.11→0.1.12 | `node error: disconnected` | retried → `storage_ready=true` in **1 s** |
| ACPI reboot | `NODE_NOT_FOUND` ×3 | retried ~3 s → resolved |
| hard reset | `NODE_NOT_FOUND` ×2 | retried ~4 s → resolved |
| upgrade 0.1.12→0.1.13 | `node error: disconnected` | retried → resolved in **1 s** |

`STORAGE_NOT_READY` in the orchestrator: **0**. Before this, 70+, and it took three attempts by hand
with the `firstboot [4/5]` pattern.

The two cold starts came from recovering the motherbee's guest agent, which died in the middle of
a test — the known flakiness — and they ended up being better evidence than the test I wanted
to run: a cold start is the race at its most extreme, everything competing at once.

### The U-7 leftover, which survived its own fix

U-7 was the watchdog asking for `fluxbee-dist-core-motherbee`, a folder the motherbee never
declares. It was fixed by routing it through `dist_sync_folders_for_hive`, and the comment says that makes
that class of drift "impossible". A fourth caller was left out: `dist_sync_hint_folder_ids` was still
on the per-role helper.

There the 404 is **worse than noisy**: a hint on the `dist` channel fans out and the first non-ok wins,
so the non-existent folder made the whole hint fail — which is exactly what an
`update category=core` waits on.

Two tests, and the second one matters: one pins the set of folders, the other pins **the caller** by reading
the source. The helper was always right, so a test that only looks at the helper passes just as
happily with the bug in. Verified by reintroducing the bug on purpose: the caller test fails, the
other does not. It is the same trap that, in the previous batch, left me five green fixtures against my own
typo.
