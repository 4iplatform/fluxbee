# 2026-09-28 — `fluxbee-factory-reset`: factory reset of the hive

> The operator's request: *"un script que limpie toda la info que los usuarios creen, una especie de
> reset to factory, para poder limpiar infra si se quiere en prod pero principalmente en dev […] no
> quiero dejarlo a nivel de admin"* ("a script that cleans all the info the users create, a kind of
> reset to factory, to be able to clean the infra if wanted in prod but mainly in dev […] I don't want
> to leave it at the admin level").

## Result

- **`packaging/fluxbee-factory-reset`**, new. It ships in the `.deb` like `fluxbee-firstboot`
  (`/usr/share/fluxbee` with a symlink in `/usr/bin`). It runs **in DRY-RUN by default**; to
  execute, it asks for `--yes` and for typing the `hive_id`. Documented in HANDBOOK §12, "Factory reset".
- Tested against a mock admin: dry-run and execution, with a kill that fails on purpose.
- **The live test is missing** in DEV (VM 270): the 4.x VPN was down.

## Operator decisions (scope)

1. **Kept:** everything that starts as system: the `SY.*` nodes and the base nodes of
   `base-nodes.json`, with their ILK, their ICH and their config.
2. **Deleted:**
   - the nodes launched by users, across the whole hive;
   - the user ILKs;
   - the message log;
   - the vault entries.
3. **Vault: only the infrastructure survives.** The AI keys are deleted too.
4. **The whole hive**, spokes included.
5. The operational history **is kept**. The routes stay "por ahora" ("for now").

## 14:00–14:45 — Survey, design and script
- **Environment:** repo · **Type:** read-only + code
- **Survey of the persistent state**, checked against the code:
  - `scripts/fluxbee_cleanall.sh` already existed, but it is the **nuclear** wipe of the old
    from-source flow: it takes the master key, `/etc/fluxbee` and the mesh with it. It does not work as a factory reset.
  - **There is no tenant deletion** in fluxbee (no action and no replication delta).
  - **Nothing marks the base nodes**: they are recognized by name, against `base-nodes.json`.
- **How it deletes each thing:** with the product's API, except where there is none:
  - nodes: `kill_node` + `purge_instance` (which already deletes the ILK, the node's secrets and its
    timers);
  - ILKs: `delete_ilk`, which replicates to the spokes;
  - secrets: `vault_delete`;
  - Archi sessions: `DELETE /api/sessions`;
  - message log: **no API**, so a `TRUNCATE` of the `fluxbee_storage` tables with
    sy-storage, sy-cognition, frontdesk and the base AI nodes stopped, and the cognition cache and
    the conversation state are deleted.
- **Bug found in my own review, before testing:** if a kill failed, the ILK step
  deleted the ILK of a node **that was still running**. Now the ILK of **every** live node is
  kept. The test with the failed kill confirms it: `ilk:broken` stayed.
- **Left out and only reported:** the `WF.*` nodes (their teardown is `wf_rules_delete`), the
  tenants, the OPA policy and the blobs.
- **Status:** OK (tested against the mock) · **Rollback:** N/A (not yet installed on any
  hive)

## 16:00–16:25 — Design decisions and WF in the reset
- **Environment:** repo + 8.x · **Type:** decision + code + live test
- **Operator decisions:**
  1. ILK and tenant deletion: **mark, and purge separately**. The tenant marks its ILKs in cascade.
  2. Unique keys stay **reserved until purged**.
  3. The reset **purges, with no backup**.
  4. User OPA: **deleted**, with a new action `opa_clear`.
  5. WF: deleted with **`wf_rules_delete` and `force`**.
- **What exists today**, checked in the code:
  - ILK has two mechanisms with no policy. The mark (`deleted_at_ms`) is only used by the merge of
    temporaries, and **it is never purged**. `delete_ilk` is a **physical** delete.
  - Tenant only has `status`, which can be `pending`, `active` or `suspended`. There is no deletion.
- **OPA:** if the router sees the SHM at version 0, it **does not unload** the policy it has in memory.
  Clearing it without restarting routers needs a change in the router, besides `opa_clear`.
  It stays in the plan.
- **WF, implemented in the reset:** it lists the workflows per hive, with the motherbee or worker role, and
  deletes them with `wf_rules_delete` and `force`. An orphan `WF.*` node is killed like a user node.
- **Live test on 8.x:**
  - the workflow `resettest` was created with the e2e definition (`compile_apply` + `auto_spawn`); the
    node `WF.resettest@motherbee` ended up HEALTHY;
  - the reset deleted it (RC=0);
  - afterwards: 0 workflows, 0 WF units, `wf-rules/` empty and 0 WF ILKs;
  - the Cloud door stayed at 200.
- **Status:** OK

## 16:30–18:30 — Identity model: mark, restore, purge (code)
- **Environment:** repo (Mac) · **Type:** code + tests. Not deployed yet.
- **Operator decisions**, all of them the recommended options:
  - purging requires marking first;
  - Cloud can only mark and restore;
  - purging a tenant that still has nodes or secrets is rejected;
  - the order is identity first and OPA after.
- **SY.identity:**
  - `ILK_DELETE` now **marks**.
  - New messages: `ILK_RESTORE`, `ILK_PURGE`, `TNT_DELETE` (with cascade), `TNT_RESTORE`
    (brings back only what the cascade marked) and `TNT_PURGE`.
  - **Reserved keys** while something is marked: provisioning, registering, adding a channel or
    creating a tenant with a reserved key returns `ILK_DELETED` or `TENANT_DELETED`.
  - DB migration **v2**: `identity_tenants.deleted_at` and `identity_ilks.deleted_reason`, in its
    own transaction.
  - Each operation persists in **a single transaction** and restores the snapshot if something fails.
  - The SHM does a full sync on every lifecycle operation, and a hole was closed: the
    incremental `IlkUpsert` re-published a marked ILK.
  - New delta `TenantDelete`, which only the primary emits.
  - Listings with `include_deleted`.
  - Optional `tenant_id` scope on ILK operations (`ILK_TENANT_MISMATCH`).
- **SY.admin:** 5 new actions in all the tables (routes, catalog, confirmation, help,
  contract and examples). `purge_tenant` **checks the vault** first (`TENANT_HAS_SECRETS`, which fails
  closed).
- **Orchestrator:** the kill with `purge_instance` and the spawn rollback now **mark and then
  purge**. Without this, the `node_name` stayed reserved and relaunching a node with the same name
  failed.
- **Cloud (SDK + io.cloud):** `delete_ilk`, `restore_ilk`, `delete_tenant` and `restore_tenant`,
  always scoped to the claimed tenant. The scope is re-validated on the admin side
  (`enforce_cloud_relay_content`, FIX-2). Purges are still **denied** to io.cloud (FIX-1).
- **Archi:** can only use the reversible ones.
- **Reset:** marks and purges ILKs, including the already marked ones, and **tenants**, in passes. Bug fixed
  before testing: the helper did not retry what failed because of dependencies.
- **Tests:** identity 51, admin 100, orchestrator 171, architect 165, SDK 166 and io-cloud 10, plus the
  reset mocks.
- **Debt noted:** `scripts/admin_action_catalog_parity_check.sh` was already failing because of old actions
  (`timer_*`, `wf_rules_*`, `publish_*`); the repo is not `rustfmt`-clean.
- **Status:** ready for `.deb` 0.1.34 · **Rollback:** `git revert`

## 18:30–19:10 — OPA: `opa_clear` + the router unloads the policy (code)
- **Environment:** repo · **Type:** code + tests. Not deployed yet.
- **SY.opa.rules** (Go), action `clear`: empties `current`, `staged` and `backup`, publishes
  "version 0 with no wasm" in the SHM and announces the reload with an all-zero hash. It is **final**: a clear has no
  rollback.
- **Router:**
  - before, an empty region was **ignored** and it kept applying the old policy until restarted;
  - now, with version 0 and no wasm, it **unloads** the user policy (`OpaResolver::unload`),
    both on the `OPA_RELOAD` notice and on the periodic check, in case the notice is lost;
  - the **system** policy has its own resolver (`system_policy.rs`) and is not touched.
- **SY.admin:**
  - `opa_clear` through two routes: `POST /opa/policy/clear`, for all hives, and
    `POST /hives/{h}/opa/policy/clear`, for one;
  - it is listed in all the tables;
  - it asks for confirmation and is operator-only: Archi cannot use it.
- **Reset:** a new step "[5/7] clear OPA" on all hives; the dry-run shows each hive's policy
  version.
- **Tests:** library 85 (with `unload`), admin 100, SDK 166; `sy-opa-rules` cross-compiles for
  Linux and passes `go vet`.
- **Debt:** the `sy-opa-rules` tests (`main_test.go`) have not compiled for a while. They use a
  `routerConn` field that disappeared with the migration to the SDK's `RouterDispatcher`; the
  stub has to be redone. The clear is validated live.
- **Status:** ready for 0.1.34

## 19:10–21:21 — Deploy 0.1.34 → regression → 0.1.35, and a real reset on 8.x
- **Environment:** 8.x (test bench) · **Type:** deploy with a snapshot first
- **0.1.34:**
  - Build on VM110 (24 min) and publish (34 packages).
  - Snapshots `pre-lifecycle-0-1-34` on the 4 VMs, rotating out the oldest per the max-3 rule.
  - `apt install` on the motherbee; the **v2 migration was applied**.
  - Core update of worker1, ingress1 and egress1: they all answered TIMEOUT, as the
    HANDBOOK documents, but they reported the new hash and their services restarted.
- **e2e through the real public Cloud door:** 26/30.
- **Regression found:** the kill with purge left the node's ILK **active**. When
  `delete_ilk` was added to the Cloud surface, the EDGE-06 gate started rejecting the orchestrator. The kill
  still answered ok, because it treats the identity failure as non-fatal. The e2e "passed" the re-spawn
  for the wrong reason: the ILK had never been marked. That is why it now **verifies that the ILK is
  purged**.
- **0.1.35**, motherbee only: any `SY.orchestrator@*` can use `delete_ilk`, like the
  sibling rule for `vault_put`. Build in 7 min.
  - e2e 27/31: the kill+purge really purges.
  - **Reset installed by the `.deb`** with real data: 1 node, 2 ILKs (among them the orphan from
    the regression), 2 secrets, **8 tenants**, OPA v5 and 13 tables, with RC=0 and 0 problems. The
    second dry-run comes out empty.
  - Cloud door at 200 with 13 actions.
- **Findings that predate the change**, for the design review:
  1. **OPA writes do not reach the spokes.** They travel as a broadcast `CONFIG_CHANGED`
     that only the motherbee's SY.opa.rules handles, and that SY.opa.rules **does not filter by
     target hive**: an `opa_apply`/`clear` aimed at worker1 **was run by the motherbee**. The
     unicast queries (`get_status`) do arrive.
  2. **worker1's identity replica rejects the admin's listing**
     (`UNAUTHORIZED_REGISTRAR`), so the replica cannot be observed from the admin. The
     replication of the mark was covered with unit tests and with the full sync at boot.
  3. The kill with purge **reports ok even if the identity removal fails**: that is why the regression was
     silent.
- **Status:** OK. **0.1.35 live.**
- **Rollback:** snapshot `pre-teardown-fix-0-1-35` or `pre-lifecycle-0-1-34`.
