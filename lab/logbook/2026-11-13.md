## IO.cloud's stray key, found and fixed (about 02:44)

- **Found, reading S4's FAILs:** IO.cloud's config.json held the stray top-level `config: {"io":
  {"edge_node": "SY.edge@gate0239x"}}` since S4 (00:42:24). The SDK takes a top-level `config` key
  as the node's whole effective config at its next start (`extract_effective_config`,
  `crates/fluxbee_sdk/src/managed_control_plane.rs` ~158-167), so any IO.cloud restart (a deploy, a
  reboot, a crash) would have made it trust `SY.edge@gate0239x` and drop every Cloud request
  through ingress1 while `HEALTHY`. IO.cloud did not restart meanwhile (pid 1949031 since 22:33:37
  on 2026-11-12).
- **Fixed on 8.x:** the config read (keys `_system`, `config`, `io`, `tenant_id`;
  `config_version` 9), then `PUT ?replace=1` with its flat keys but `_system` and `config` (`io`
  naming `SY.edge@ingress1`, and `tenant_id`, built from the read), and read back: keys `_system`,
  `io` and `tenant_id`, `config_version` 10, `io.edge_node` `SY.edge@ingress1`, no stray key;
  IO.cloud `RUNNING` `HEALTHY` on the same pid. Only S4's write had that shape (the gate tools' one
  config `PUT`).
- **The product bug behind it:** A-346 (medium, FINDINGS), `set_node_config`'s help describes a body
  the HTTP route does not take: the help's `config` and `replace` fields and its example, where the
  route takes the body as the patch and `replace` from `?replace=1`. A caller who follows the help
  gets 200 and plants a top-level `config` key the node takes at its next start. Options for the
  operator: (a) the help says the HTTP body is the patch and `?replace=1` replaces it whole; (b) the
  orchestrator refuses a top-level `config` key in a patch, as it refuses `_system`; (c) the SDK
  drops the wrapped form. Recommended: (a) with (b).
