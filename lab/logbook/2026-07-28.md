- **Findings / risks:**
  1. **The second network is NOT wired at the Proxmox level** — `vmbr1` on `nic1` is still missing.

     irreversible → needs approval**).
  4. **Addressing**: the admin network is DHCP, but `add_hive` records each spoke's address; if the
     lease changes, the record goes stale. → Proposal: **a DHCP reservation by MAC** on the 8.1 router.

## 13:10 — Nested virt: BLOCKER found (evidence)

- **Environment:** prod · **Type:** read-only
- **Goal:** check whether KVM works before investing in the template.
- **Executed:** `GET /api2/json/nodes/pve/status` → `cpuinfo`
- **Result:**
  - the flags contain **`hypervisor`** (confirms it runs virtualized on VMware)
  - they **do NOT contain `vmx`** (Intel VT-x)
  - **`hvm: ""`** (empty) ⇒ **no hardware virtualization**
  - topology: **8 sockets × 1 core** (suboptimal; 1 socket × 8 cores is better)
- **Conclusion:** **KVM NOT available.** The VMs will not boot with `kvm=1`; with `kvm=0` it would be
  TCG emulation (not viable for a hive with postgres + ~20 nodes).
- **Action required (operator, in VMware, with the VM powered off):**
  - ESXi/vSphere: CPU → **"Expose hardware assisted virtualization to the guest OS"** (`vhv.enable="TRUE"`)
  - Workstation/Player: Processors → **"Virtualize Intel VT-x/EPT or AMD-V/RVI"**
- **Re-check:** the same query; `vmx` must show up in the flags and `hvm` must not be empty.
- **Status:** BLOCKER OPEN · **Rollback:** N/A

## 13:20 — Virtual internal network 10.10.10.0/24 created (SDN) ✅

- **Environment:** prod · **Type:** **irreversible** (host network) — **authorized by the operator**
- **Goal:** move fluxbee's internal traffic off the shared `8.x` network onto a network of its own,
  with the Proxmox host acting as router/NAT.
- **Prior check:** SDN supported (`libpve-network-perl 1.6.5`, `ifupdown2 3.3.0`, IPAM `pve`),
  no pre-existing zones/vnets.
- **Executed:**
  ```bash
  POST /cluster/sdn/zones            type=simple zone=fluxint ipam=pve nodes=pve
  POST /cluster/sdn/vnets            vnet=fbint zone=fluxint
  POST /cluster/sdn/vnets/fbint/subnets  subnet=10.10.10.0/24 type=subnet gateway=10.10.10.1 snat=1
  PUT  /cluster/sdn                  # apply
  ```
- **Result:**
  - Task `UPID:pve:00029086:...:reloadnetworkall` → **exitstatus OK**
  - Zone `fluxint` → **status: available**
  - **`fbint` active as a `vnet`-type bridge**, available for VMs
  - Subnet: `10.10.10.0/24`, gateway `10.10.10.1`, **`snat: 1`** ← the host acts as router/NAT
  - **`vmbr0` intact**, the session did not drop, uptime unchanged (no reboot)
- **Functional test pending:** that a VM on `fbint` reaches `10.10.10.1` and gets out to the internet
  through NAT. **It cannot be tested until the nested virt blocker is solved** (no VM can boot).
- **Design note:** a **Simple zone = node-local**. If there is a second Proxmox host tomorrow, this zone
  **does not extend** to it: we would have to migrate to **VXLAN/EVPN**. Noted for when it scales.
- **Positive side effect:** since it is our own network, **the DHCP reservation problem goes away** —
  the internal IPs are assigned statically by cloud-init and are stable for `add_hive`.
- **Status:** OK (created and applied; functional test pending)
- **Rollback:** `DELETE /cluster/sdn/vnets/fbint/subnets/fluxint-10.10.10.0-24`,
  `DELETE /cluster/sdn/vnets/fbint`, `DELETE /cluster/sdn/zones/fluxint`, then `PUT /cluster/sdn`.
