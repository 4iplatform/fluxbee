- **Entorno:** prod

- **Objetivo:** confirmar la red doble descrita por el operador (admin 8.x DHCP + segunda placa a

- **Ejecutado:**

- **Resultado:**
  - **`vmbr0`** — `active=1`, `192.168.8.207/24`, gw `192.168.8.1`, `bridge_ports=nic0`,
    `method=static` (el host tiene IP fija aunque la red sea DHCP: normal para el hipervisor).
  - **`nic0`** — `active=1`, `exists=1`, altnames `enp11s0` / `enx000c292761aa`.
  - **`nic1`** — `exists=1` pero **SIN `active`** → la placa existe pero está **caída y sin configurar**.
    altnames `enp19s0` / `enx000c292761b4`. **No hay `vmbr1`.**
  - **MAC OUI `00:0c:29` en ambas placas → VMware, Inc.** ⇒ **este Proxmox corre como VM sobre VMware**;
    las dos NICs son virtuales.
  - Cluster: nodo único `pve`.
- **Hallazgos / riesgos:**
  1. **La segunda red NO está cableada a nivel Proxmox** — falta crear `vmbr1` sobre `nic1`.
  2. **Capa VMware por debajo**: a qué router llega `nic1` lo define el *port group* de VMware,
     invisible desde Proxmox. **Riesgo de virtualización anidada**: KVM dentro de VMware requiere
     *"expose hardware assisted virtualization"*; si está apagado las VMs no arrancan o van lentísimas.
     → **Verificar antes de construir el template** (ya nos mordió en el lab).
  3. **No se puede verificar el link/carrier de `nic1` desde la API** (muestra configuración, no estado
     de enlace) — límite Nivel-3 de `METHOD.md` §2. Destrabe: dato del port group VMware,
     `ip -br link show enp19s0` en el host, o crear `vmbr1` y probar (**cambio de red del host =
     irreversible → requiere aprobación**).
  4. **Direccionamiento**: la admin es DHCP, pero `add_hive` registra la dirección de cada spoke; si el
     lease cambia, el registro queda viejo. → Propuesta: **reserva DHCP por MAC** en el router 8.1.
