## The operator's call on A-175

- **The question asked:** what is the egress's alert for on the motherbee? Is it log, or does the
  motherbee have something to do with it? *"la idea de hacer el log general del sistema es mandar
  a stream como ahora lo hace el router con los mensajes al storage, a un log general de todo el
  sistema, mismo mecanismo descentralizado.. eso no está ni planeado.. si es log podemos pensarlo
  después"*.
- **Read in the code, it is log:**
  - nothing reads a drift alert to act; the only readers are `GET /drift-alerts` and
    `GET /hives/{hive}/drift-alerts`, for the operator and Archi;
  - an orchestrator corrects its drift whether or not it records the alert.
- **It is not only the egress:** every spoke's posture checks stay in its own file too (an active
  firewall on a worker, the ingress's SSH table).
- **So A-175 waits for the system's log** (router-stream-v1 §8). My proposal of 2026-11-07, each
  alert sent to the motherbee, was per-feature remote logging, which the direction of 2026-10-30
  rules out.
- **Until then:** a read for another hive says it holds only what the motherbee recorded (the
  sixth release). The docs say where a spoke's alerts stay.

## A-181, talked over: a hive's shared config travels in the update

- **Asked first:** do the orchestrators have channels of their own? No. They are nodes of the mesh:
  - the system policy's rule (3) gives the direction: the motherbee's orchestrator commands and
    reads, and a spoke's orchestrator does neither toward any hive;
  - rule (2) lets SY.admin send `SYSTEM_UPDATE` and node config to any hive;
  - Syncthing carries files, and SSH is used only at the join.
- **The operator's proposal:** `SYSTEM_UPDATE` carries the hive.yaml changes, and each orchestrator
  applies them locally. Evaluated, it closes on four conditions:
  1. it carries the state, not a diff;
  2. only the shared keys travel, never the control path;
  3. each orchestrator validates and writes atomically, and keeps the previous file;
  4. a hive that missed it shows in `/versions`.
- **Read in the code on the way:**
  - The same gap bites the AI model (worker1's was edited by hand at 0.1.72) and a release's new SY
    node for workers.
  - The role's `system_nodes` decides which core components a spoke installs, so the config must
    go with the core.
- **The operator's direction:** *"Todo lo define una versión de software … quedaría todo dentro del
  canal de update"*. That settles it in the core update itself, where I had proposed a category of
  its own.
- **The design's first draft:** docs/hive-config-update-v1.md.
- **The operator's calls on it:**
  - Yes to the motherbee's file taking the release's keys, under one rule: every hive's config is
    at one version (*"Si cambia versión cambia todo, como un pedazo de software de update"*).
  - The keys stay as listed.
  - The blob's switch goes.
  - The worker that joined before the egress is apart, for later.
- **The rule in the doc (§7):**
  - One version for the installation, raised by each release and each operator's change.
  - An update is done when every hive is on it.
  - A hive that was down gets it from the motherbee when it is back. That is the one automatic
    step, proposed.
