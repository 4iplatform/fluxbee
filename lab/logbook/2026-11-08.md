# 2026-11-08 — A spoke's drift alerts are log (A-175 parked for the system's log); the sweep's bugs read again: the router's fifth release (A-177, A-178, A-179)

## The operator's call on A-175

- **The question asked:** what is the egress's alert for on the motherbee? Is it log, or does the
  motherbee have something to do with it? *"la idea de hacer el log general del sistema es mandar
  a stream como ahora lo hace el router con los mensajes al storage, a un log general de todo el
  sistema, mismo mecanismo descentralizado.. eso no está ni planeado.. si es log podemos pensarlo
  después"*.
- **Read in the code, it is log:**
  - nothing reads a drift alert to act; the only readers are `GET /drift-alerts` and
    `GET /hives/{hive}/drift-alerts`, for the operator and Archi;
  - an orchestrator corrects its drift whether or not it records the alert.
- **It is not only the egress:** every spoke's posture checks stay in its own file too (an active
  firewall on a worker, the ingress's SSH table).
- **So A-175 waits for the system's log** (router-stream-v1 §8). My proposal of 2026-11-07, each
  alert sent to the motherbee, was per-feature remote logging, which the direction of 2026-10-30
  rules out.
- **Until then:** a read for another hive says it holds only what the motherbee recorded (the
  sixth release). The docs say where a spoke's alerts stay.

## The sweep's bugs, read again in the code

The operator: *"por los bugs, si quedan claros que son bugs continuá por ahí"*.

- **Clear, numbered:**
  - **A-177:** a second rt-gateway started by hand deletes the live router's sockets, binds its
    own, and opens the same shared memory and stream. This is how 0.1.60's `rt-gateway --version`
    broke the socket paths.
  - **A-178:** a missing or unknown `wan.mtls` runs the WAN in plaintext. The fix copies
    `identity.sync.auth`'s fail-closed rule from the identity audit's F-01.
  - **A-179:** nothing checks the baked system policy against its Rego.
  - **A-180,** found while checking A-177: the same 0.1.60 incident ran a second sy-orchestrator.
    Its boot acts on the host before it joins the router.
- **Not a plain bug: A-181,** the blob folder turned on after the joins. No action turns the
  blob's sync on after the install, and a spoke's hive.yaml is written once, at its join. How a
  motherbee setting reaches the hives that joined before it is the operator's call.
- **To read again before building:** the SDK items, and the sweep's worker joined before the
  egress existed, which never gets `egress.gateway_ip`. Fixing that one changes a live worker's
  default route, so it goes to the operator first.

## The fifth release, 0.1.111, built

- **A branch each, tested by GitHub's CI:** A-177 (the router's argument guard and instance
  lock), A-178 (`wan.mtls` fails closed), A-179 (the baked policy checked against its Rego).
  - On 8.x the four hive.yaml already say `mtls: required`: A-178 changes nothing there.
- **A-179's first CI run failed, and that was the finding:** the compiler recorded a random
  temporary path in every wasm, so no two compiles were the same.
  - Compiling the current Rego with each committed file's own recorded path gave both files byte
    for byte: the baked policy was not stale, and the compile is the same on the Mac.
  - The compile now reads the module as `policy.rego`; both wasm were compiled again.
  - Two sy-opa-rules tests had relied on two compiles differing; they now compile policies that
    differ.
- **The review round, one reviewer for the three:**
  - A-177's lock was on the disk, where a full or read-only disk would have kept the router down.
    It is on tmpfs now, only another holder refuses a start, and the lock lives until the process
    ends.
  - A-179's guard ran a test filter, which a renamed test would have passed. It runs the whole
    package now, and it also checks what the router bakes.
  - A-178: nothing.
- **Integrated** on daily by rebase, the branches deleted; build of `cc01f86f`.
