## The shape of 3c, decided from the code

- **The write travels as `SYSTEM_UPDATE` category `config`,** with a `write`, to the motherbee's
  orchestrator. That orchestrator is the only writer.
  - Policy rule (2) already admits SY.admin@motherbee toward every orchestrator.
  - A new message type would have needed the router's policy, which ships alone.
- **Every hive applies a version** with the usual form (version and hash). It answers
  `sync_pending` until its copy matches. Then it restarts only the start readers whose engine
  changed: SY.cognition, and SY.frontdesk.gov on the motherbee.
- **SY.admin's executor and Archi are never restarted by a config update.** They re-read the file
  at their next use, as ai.generic does at each request.
  - Archi may be the caller, and a restart would cut its reply and the operator's chat.
  - This replaces the design's "SY.admin restarts last".
- **Who reaches what:**

    operator confirms.
  - `get_installation` is open to Archi.

### The shape, decided from the code

- **A-198** (branch `coa/a-198`):
  - Any SY.admin mesh reply the SDK refuses for its size becomes a small `REPLY_TOO_LARGE`
    answer, with its size and how to page.
  - A write's answer keeps its outcome, so a caller never retries blindly.
  - The hops behind SY.admin (SY.identity's list, the orchestrator's versions, SY.vault's list)
    page internally or answer the same way.
  - Optional `limit` and `cursor` where a list grows, with the defaults unchanged.
  - A plan's answer bounds each step's output, so every step's status arrives.
  - Budget tests for the catalogs.
- **Stage 4** (branch `coa/hive-config-s4`):
  - `update_installation` brings every hive to what the motherbee holds: its core, and its
    installation file.
  - Its state is on disk, so SY.admin resumes it after a restart. Each hive goes core first, then
    config.
  - `set_installation_ai` runs the same machinery.
  - `get_installation_update` is the read.
  - `ops.py deploy` calls the update from 0.1.123 on, and keeps the old path below it.
  - The automatic step finishes the update, once per hive and target, for a hive that answered
    nothing and comes back.
  - The config apply's first wait drops from 2 s to 0.5 s.
- **The exclusions, read from §6:**
  - **A hive the operator rolled back** keeps its core through every installation-wide run,
    unless the run names it. The automatic step touches nothing on it. An explicit run still
    applies the config, which replaces no binary.
  - **A hive ahead of the motherbee** is left alone by the automatic step only. An explicit run
    moves it, since that is the installation's rollback.
  - **A hand-edited copy** gets no config apply.
- **The build:** two agents in parallel, one per branch. Whichever finishes second is rebased onto
  the other.

- **The review round:** two reviewers, one on what the change could break, one on the new paths.
  Nothing high against PROD's state today. Six mediums:
  - one failed listing of the hive registry closed the open update as `done`;
  - Archi never verified a release's rollout, which answers 202 while cores restart;
  - a rolled-back hive kept the update open forever, with re-reads every 30 s;
  - `left_out` never cleared, so a release that drops a node never read as settled;
  - the reads went through the motherbee orchestrator's single admin worker, piling up behind a
    held forward;
  - a resumed update's target could go stale after the motherbee was downgraded, and the automatic
    step would then install the release being rolled back.
- **Among the lows:**
  - a timed-out core call was read as not answered;
  - a busy hive could be skipped silently;
  - nothing stopped two runs at once;
  - `ops.py` had a thread race and printed transitions for hives that had none;
  - the docs drifted from the code.
- **The fixes, decided:**
  - one read per hive, with cadences by state (3 s in flight, shared memory for an absent hive,
    10 min for held or failed hives);
  - a look at once after a per-hive `update` or `core_rollback`, a join or a removal, and a read;
  - a `held` state, for A-5's one allowed divergence: the update answers 200, `ops.py` exits 0
    with a warning, and Archi verifies the run while naming the divergence;
  - Archi waits for a rollout before judging it;
  - the settle judged by `settled`;
  - no act on a stale target;
  - one explicit run at a time.
- **Recorded apart:** A-199, the motherbee orchestrator's admin worker, which serves one request at
  a time (already a known limit in `docs/wf-standard-path-v1.md`).
