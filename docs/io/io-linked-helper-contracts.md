# Technical specification — `adapter ↔ IO.linkedhelper` v1 contracts
## Minimal messages and responses

> Document updated to reflect the current split of responsibilities of the `IO.linkedhelper` node.

---

# 1. Scope

This document covers:

- the adapter's minimal event types;
- the node's minimal response types;
- the minimal conceptual shape of each family;
- the minimal fields needed to move forward.

It does not cover yet:

- a final, closed JSON schema;
- advanced payloads;
- attachments in detail;
- message editing/cancellation;
- the final `get-config` / `set-config` contract.

---

# 2. General correlation rule

Every item sent by the adapter must have a correlatable identifier.

Every response from the node, except a pure heartbeat, must be able to reference the original event.

## Minimal definition already acceptable to move forward
Correlation must exist, no matter what.

For the first implementation, the acceptable operational criterion is:

- the adapter guarantees `event_id` uniqueness within itself;
- the node treats the event's effective key as `adapter_id + event_id`;
- and the node's responses can reference the original event by returning `event_id`, with `adapter_id` as the natural context of the channel.

## Truly open
Only the fine detail is left to settle, whether to use:
- only `event_id`;
- `request_id + event_id`;
- or another combination.

---

# 3. Minimal adapter events (v1)

## 3.1. `heartbeat`

### Goal
Keep the exchange going and pick up pending items when the adapter has no new outgoing events.

### Minimal conceptual fields
- `id`
- `adapter_id`
- `managed_instance_id`
- `local_instance_id` optional
- `timestamp`

### Note
It is not a simple keepalive: it also serves to pick up results and configuration changes.

---

## 3.2. `profile_create`

### Goal
Report the discovery of a new profile.

### Current semantics
It does not imply that the adapter can automate.
Its job is to let the node create the provisional ILK and start the internal flow.

### Minimal conceptual fields
- `id`
- `adapter_id`
- `managed_instance_id`
- `local_instance_id` optional
- `external_profile_id`
- `display_name`
- `metadata` optional

### Important restriction
- `external_profile_id` is generated by the adapter.
- It must guarantee global uniqueness across all adapters.
- The adapter does not receive the resulting provisional ILK.
- Even if the adapter builds it internally as a composite when needed, it must reach the node as a canonical `external_profile_id`, ready to use.

### Potentially useful metadata
- observed email
- observed timezone, if it exists and is reliable
- other visible profile data

---

## 3.3. `conversation_message`

### Goal
Represent a consolidated communication from an external contact to a profile.

### Main restriction
It is only emitted for profiles that already have a final/usable ILK and whose LH ICH has automation enabled.

### Minimal conceptual fields
- `id`
- `adapter_id`
- `managed_instance_id`
- `local_instance_id` optional
- `profile_ilk`
- `contact_name`
- `contact_external_composite_id`
- `contact_lh_person_id` (origin reference)
- `conversation_external_id`
- `content`

### About the contact
`contact_external_composite_id` must be read, for the node's practical purposes, as the contact's canonical `external_id`.

It may be a composite id built by the adapter to guarantee global uniqueness, but:

- the node should not depend on taking it apart;
- the node treats it as an opaque canonical identifier, ready for identity resolution.

The `contact_lh_person_id`:
- is useful for traceability;
- but must not be used on its own as the global canonical identity.

### About the content
It must be thought of as general conversational content.
In v1 it may be text, but it is better not to assume it will always be a text-only message in future iterations.

### MVP behavior when contact resolution fails
For the MVP, if the node cannot resolve the contact's minimal identity:
- the conversation does not move forward;
- it returns an error;
- and it adds no extra complexity of long waits on the node side.

---

## 3.4. `system_alert`

### Goal
Report non-conversational events of the LH channel.

### Possible cases
- profile instance/state;
- operational changes;
- channel alerts;
- other non-AI events.

### Current status
It is recognized as a valid family.

## Truly open
What is still pending is the exact cut of the minimal set of alerts that will go into the MVP, and the concrete shape of its payload.

---

## 3.5. Potential future event: `profile_update`

Today it is **not part of the minimal v1 set**.

### Reason
With the current split:
- the adapter is no longer the strong source of truth for the profile;
- Fluxbee/core holds most of the identity/configuration;
- and today there is not enough useful signal on the adapter side to justify it in a first version.

### Status
It is explicitly left as:
- a potential future event,
- not implemented in the first version.

---

# 4. Minimal node responses (v1)

These are kept as top-level families:

- `ack`
- `result`
- `heartbeat`

---

## 4.1. `ack`

### Goal
Indicate that the node received and accepted the event for processing.

### Minimal conceptual fields
- `response_id`
- `adapter_id`
- `event_id`
- `type = ack`

### Note
It does not imply a final resolution.

---

## 4.2. `result`

### Goal
Represent the current operational result of a previous event.

### Minimal conceptual fields
- `response_id`
- `adapter_id`
- `event_id`
- `type = result`
- `status = success | error`
- `result_type`
- `payload` optional
- `error_code` optional
- `error_message` optional
- `retryable` optional

### Important rule
`error` is not a separate message.
It is a `result` with `status = error`.

### Base catalog already on track
For the MVP, the base set that is already defined well enough is:
- `profile_ready`
- `conversation_processed`
- `automation_enabled`
- `automation_disabled`
- `identity_error`
- `promotion_error`
- `blocked_profile`

### About conversational results
It must not be assumed that the conversational payload is always a mandatory text `message`.
It must be able to represent more general outgoing content.

---

## 4.3. `heartbeat`

### Goal
Respond when there is nothing else to return, or as the minimal response to an empty poll.

### Minimal conceptual fields
- `response_id`
- `adapter_id`
- `type = heartbeat`
- `timestamp`

## 4.4. Current intermediate HTTP envelope

In the node's current implementation, the top-level HTTP response also includes:

- `ok`
- `accepted_at`
- `response_id`
- `adapter_id`
- `actions`
- `items`

Current rule:

- `items` is still the main carrier of `ack` / `result` / `heartbeat`;
- `actions` exists for compatibility with the direct path without Edge;
- in the current runtime, `actions` is returned empty.

---

# 5. Beacon results that are already on track

## 5.1. `profile_ready`
When the node detects that the ILK has moved to a usable state, it returns it to the adapter.

### Minimal expected payload
- `external_profile_id`
- `ilk_id`
- `ich_id`

## 5.2. `automation_enabled`
When the LH ICH becomes enabled.

### Minimal expected payload
- `external_profile_id`
- `ilk_id`
- `ich_id`

## 5.3. `automation_disabled`
When the LH ICH becomes disabled.

### Minimal expected payload
- `external_profile_id`
- `ilk_id`
- `ich_id`

## 5.4. Resolution/promotion errors
The node must be able to return errors related to:
- inability to promote the profile;
- inability to resolve the identity;
- or internal failures of the registration flow.

---

# 6. Current intermediate HTTP request

For the current intermediate path, the request to the node must include:

- header `X-Fluxbee-Adapter-Id`
- header `Authorization: Bearer <adapter_secret>`
- body with `adapter_id`
- body with `managed_instance_id`
- body with `local_instance_id` when applicable
- `mode = "events" | "heartbeat"`
- `items = []` or a batch of events

Minimal conceptual shape:

```json
{
  "request_id": "req_123",
  "adapter_id": "adp_123",
  "managed_instance_id": "lhmi_001",
  "local_instance_id": "123456",
  "mode": "events",
  "items": [
    {
      "id": "evt_001",
      "type": "profile_create",
      "payload": {}
    }
  ]
}
```

Defensive validations of the current node:

- the body's `adapter_id` must match `X-Fluxbee-Adapter-Id`;
- `managed_instance_id` must match the node's configuration;
- `local_instance_id` must match when the node has it configured;
- the bearer must match the secret resolved from Vault.

---

# 7. What is still current from earlier contracts

Kept:

- `ack`
- `result`
- `heartbeat`
- `result` with `status` + `result_type`
- `conversation_message` as a valid event family

Redefined:

- `profile_create` as a discovery that triggers a provisional ILK;
- `conversation_message` only for profiles with a final ILK and LH automation enabled;
- `result` must explicitly cover config/ICH changes and profile ready.

Removed from the v1 minimum:

- `profile_update`

---

# 8. Real open items

## 7.1. Exact shape of each payload
The final schema is still pending.

## 7.2. `system_alert`
Still pending:
- the minimal MVP subset;
- and the exact payload.

## 7.3. Exact correlation
The fine detail of the final id model is not settled.

## 7.4. Attachments and non-text payloads
They are not settled yet, although the contract should not block them in the future.

## 7.5. `get-config` / `set-config`
They remain tentative and are not settled in this document.

---

# 9. Summary

The minimal v1 contracts are:

## Adapter → node
- `heartbeat`
- `profile_create`
- `conversation_message`
- `system_alert`

## Node → adapter
- `ack`
- `result`
- `heartbeat`

With the criterion that:

- a discovered profile first enters the provisional flow;
- the adapter does not consume provisional ILKs;
- `conversation_message` only exists once the profile is ready and enabled for automation through its ICH;
- `profile_update` is left out of the MVP and kept as a potential future event.
