# Fluxbee — pendientes al 2026-07-12 (cierre de sesión)

Lista consolidada de lo que **falta**, desde donde empezó esta sesión (auditoría SY.edge → io.cloud →
OPA-dual → auditoría del router). Lo **hecho** está en los commits `b1932e1`…`e2fda22` y en las
memorias. Ordenado por prioridad dentro de cada área.

**Actualización 2026-07-17:** el contrato alpha acepta el bearer de servicio de Cloud como autoridad.
Quedaron implementados `create_tenant`, `put_token` y `provision_node`, con gates en edge, `IO.cloud`
y `SY.admin`. Los puntos A.1 y A.3 ya no bloquean el provisioning alpha; se conservan abajo para
registrar el trabajo de producción pendiente.

## A. io.cloud / Fluxbee Cloud (la vertical que construimos — lo que falta para producto real)

1. **[PRODUCCIÓN, DIFERIDO] Identidad de usuario final por tenant.** En alpha el bearer de servicio
   autentica a Cloud y Cloud asegura el `tenant_id`; esa decisión permite provisioning hoy. Antes de
   delegar a tokens de usuario o ampliar acciones falta Cloud→sujeto-verificado→tenant (§9.1 de
   `docs/io-cloud-spec-v1.md`).
2. **[PRODUCTO] Runtime `io.wapp` real.** `provision_node` relaya `run_node` correctamente
   (lab-validado: llega al orchestrator, tenant inyectado, gate OK) pero devuelve
   `RUNTIME_MANIFEST_MISSING` — **no hay runtime publicado**. Falta el adaptador `io.wapp` (cliente
   WhatsApp + webhooks) + publicar su runtime. Ídem otros proveedores (gmail, etc.).
3. **[PROVISIONING ALPHA CERRADO] IO.cloud como producto Cloud real (EDGE-09).** El relay ya implementa
   `create_tenant`, `put_token` y `provision_node`, exige entrada edge/ICH válida y propaga
   `request_id`. Más allá del provisioning siguen pendientes dispatch a conversación, identidad de
   usuario final y un cliente saliente al backend Cloud.
4. **`io.archi` forwarding (caso 2, diferido).** HTTP per-tenant a `SY.architect` tras login; necesita
   aislamiento de tenant + auth de sesión + **streaming (websocket/SSE)** que el edge hoy no hace.
5. **Respuestas grandes.** Límite de frame 128KB. Paginación para estructurado. El circuito de
   `io-blob-spec-v1.md` quedó implementado y su infraestructura fue validada en Linux/Proxmox:
   admin authority, `IO.blob` curator, Syncthing publico one-way, `/public/<capability>` y teardown.
   Falta el smoke de producto desde un AI/IO real para publish/expiry/unpublish.
6. **Cliente fino de SDK** para `list_cloud_actions` (conveniencia opcional; el catálogo ya vive en admin).

## B. OPA-dual / policy (cerrado, con futuro acordado)

7. **[FEATURE] Fase 4 — reglas system runtime-editables.** 2ª región SHM `/jsr-opa-sys-<hive>` +
   writer privilegiado alimentando el resolver. Hoy es **bakeado** (recompilar para cambiar reglas).
   Esto es lo que habilita "agregar regla y listo" sin rebuild. El contrato `authorize_system` no cambia.
8. **Reachability al seam/OPA (el "paso 3").** `vpn_allows_between` + helpers `edge_*/is_*` siguen
   **hardcodeados en Rust** — solo la capa de AUTORIDAD se hizo OPA. Es la otra mitad de la policy.
9. **Helpers de subsistema a OPA.** admin/architect/identity llaman al seam (Rust); extenderlos a
   evaluar OPA es un paso posterior.
10. **Query de capacidades/routeo node-facing.** El "¿puedo routear a Y? / ¿puedo la acción A?"
    **diseñado pero NO construido** (solo existe `list_cloud_actions` para acciones de admin). Hoy los
    nodos aprenden reachability solo reactivo (UNREACHABLE/TTL). Proyección limpia de authority (para
    "puedo A"); para "puedo routear a Y" primero conviene el paso 3 (reachability centralizada).
11. **Automatización de build de `system.wasm`.** No hay `build.rs`/CI que regenere el wasm desde
    `system.rego` — es paso manual (compile-file + commit), guardado solo por el shadow-verify test.

## C. Auditoría del router (esta sesión — findings diferidos)

12. **[MEDIUM] Authz de `CONFIG_SET`/`CONFIG_GET` de nodos IO.** Un nodo same-VPN autenticado puede
    reconfigurar un nodo IO sin check de origen (`apply_io_config_set`, sin authz; no está en
    `PROTECTED_SYSTEM_ACTIONS`). **Fix limpio (central):** chequeo de origen en el SDK
    `crates/fluxbee_sdk/src/node_config.rs :: parse_node_config_request` — exigir `src_l2_name` = `SY.*`
    (los senders legítimos — orchestrator/admin/architect — son todos SY.*). Un fix cubre todos los nodos.
13. **[LOW] Ramas de relay `UNREACHABLE`/`TTL`** (WAN ~2827, peer ~3628) entregan a un nodo local
    **sin `vpn_allows_between` ni stamp**. Bajo impacto (verbos no-protegidos, correlación por UUID
    trace, requiere peer autenticado). Tensión de diseño: esos frames son router-generados y no
    resuelven como nodo. Defense-in-depth opcional: allowlist explícita de control-frames + stamp.
14. **[cosmético] Campos write-only** `OpaWasm.instance` (renombrar `_instance` — puede ser lifetime
    anchor de wasmtime), `PeerRouter.name` (unused). **Y:** el SDK `node_config.rs` `is_node_config_*`
    todavía compara `== SYSTEM_KIND` **case-sensitive** (el router ya lo normaliza/gatea, así que es
    defense-in-depth) — alinear con `eq_ignore_ascii_case` como el router.

## D. Residuales de seguridad de las auditorías previas del edge
