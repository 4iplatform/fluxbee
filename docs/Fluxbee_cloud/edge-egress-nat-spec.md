# Fluxbee Cloud - Edge Egress NAT Specification

**Status:** v0.1 draft
**Date:** 2026-05-27
**Audience:** `SY.orchestrator`, `RT.edge`, `RT.gateway`, deployment tooling
**Related:** `edge-control-protocol.md`, `../05-conectividad.md`, `../07-operaciones.md`

---

## 1. Purpose

This document defines the first practical egress model for Fluxbee deployments where all Fluxbee hives run on an internal network and only one or more edge hosts have internet access.

The goal is intentionally narrow:

- Internal hives can make outbound HTTPS calls to internet services, such as OpenAI.
- The outbound path is routed through a controlled edge host.
- No inbound internet access is opened toward workers.
- The model is simple enough for `SY.orchestrator` to provision through `add_hive`.

This document does not replace the `RT.edge` ingress design. It complements it.

---

## 2. Terms

| Term | Meaning |
|------|---------|
| **Motherbee** | The control center of the Fluxbee deployment. It remains the authority for hive inventory, provisioning, and operational state. |
| **Edge hive** | A Fluxbee hive with `role: edge`. It runs the minimal edge control/runtime services and owns internet egress for an internal LAN. |
| **Worker hive** | A normal internal hive without direct internet access. |
| **Ingress** | Public internet traffic entering Fluxbee through `RT.edge`. |
| **Egress** | Internal Fluxbee nodes making outbound internet connections through NAT on the edge host. |
| **WAN** | Fluxbee inter-hive WAN handled by `RT.gateway`. In this context, WAN means the Fluxbee gateway link to motherbee, not generic public internet. |
| **LAN** | Internal private network where workers and the edge's internal interface live, for example `192.168.8.0/24`. |

---

## 3. Design Principles

### 3.1 Motherbee stays central

The edge is important, but it is not the center of the system. Motherbee remains the operational source of truth.

The edge participates as a managed hive:

- It has its own `hive_id`.
- It runs `SY.orchestrator`.
- It runs `RT.gateway` to connect to motherbee.
- It runs a local `SY.identity` replica so `RT.edge` and the local router can read `/jsr-identity-<edge_hive>`.
- It can later run `RT.edge` for public ingress.

### 3.2 Ingress and egress are separate

`RT.edge` handles ingress:

```text
public client -> RT.edge -> Fluxbee L2/WAN -> motherbee/workers
```

Egress is OS routing/NAT:

```text
worker process -> default route -> edge LAN IP -> NAT -> internet
```

NATS does not participate in egress. `RT.gateway` does not carry generic internet traffic. Calls to OpenAI are normal outbound HTTPS connections from the node process.

### 3.3 The same orchestrator binary should support edge role

There should not be a separate edge orchestrator binary. The existing `SY.orchestrator` should support:

```yaml
role: edge
```

This keeps deployment and updates aligned with motherbee and worker hives.

### 3.4 Simple config first

The common case should not require interface names, firewall backend choices, or many policy options.

Motherbee should only need to declare the edge hive and its LAN gateway IP:

```yaml
egress:
  edge_hive: "edge-1"
  edge_ip: "192.168.8.1"
```

The edge host can auto-detect:

- WAN interface from the default route to the internet.
- LAN interface from `edge_ip`.
- LAN CIDR from the interface address.

Overrides can be added later if real deployments need them.

## 4. Target Topology

```text
                         INTERNET
                            |
                       edge WAN NIC
                    +----------------+
                    | edge-1         |
                    | role: edge     |
                    | RT.gateway     |
                    | SY.orchestrator|
                    | future RT.edge |
                    +----------------+
                       edge LAN NIC
                         192.168.8.1
                            |
                    internal LAN 192.168.8.0/24
                            |
        +-------------------+-------------------+
        |                   |                   |
   worker-1            worker-2            motherbee
   no internet         no internet         control center
   gw 192.168.8.1      gw 192.168.8.1
```

Motherbee remains the control center. The edge is a managed route for internet egress and, later, public ingress.

## 5. Hive Configuration

### 5.1 Motherbee

Motherbee declares the edge used for outbound egress:

```yaml
hive_id: "motherbee"
role: motherbee

wan:
  listen: "192.168.8.10:9000"
  gateway_name: "RT.gateway"

egress:
  edge_hive: "edge-1"
  edge_ip: "192.168.8.1"
```

`wan.listen` is still the Fluxbee WAN listener for hive-to-hive traffic. It is not the public internet interface.

### 5.2 Edge hive

The edge hive is generated by `add_hive` with `role=edge`:

```yaml
hive_id: "edge-1"
role: edge

wan:
  gateway_name: "RT.gateway"
  uplinks:
    - address: "192.168.8.10:9000"

egress:
  enabled: true
  edge_ip: "192.168.8.1"
  ipv6: "blocked"

identity:
  sync:
    upstream: "192.168.8.10:9100"
```

`edge_ip` is the LAN-side gateway IP used by workers.

`identity.sync.upstream` points to motherbee's identity sync endpoint. The edge identity service runs as a replica, not as the primary identity authority.

### 5.3 Worker hive

Workers receive a small egress section during `add_hive`:

```yaml
hive_id: "worker-1"
role: worker

wan:
  gateway_name: "RT.gateway"
  uplinks:
    - address: "192.168.8.10:9000"

egress:
  gateway_ip: "192.168.8.1"
  ipv6: "blocked"
```

The worker target state is simple:

- Default IPv4 route via `192.168.8.1`.
- DNS works.
- IPv6 egress is blocked or reported as unmanaged.

## 6. `add_hive` Behavior

### 6.1 API

`add_hive` should accept an optional role:

```json
{
  "hive_id": "edge-1",
  "address": "192.168.8.1",
  "role": "edge"
}
```

If `role` is omitted, it defaults to `worker`.

Allowed roles for this flow:

| Role | Meaning |
|------|---------|
| `worker` | Normal internal hive. |
| `edge` | Edge hive with egress NAT responsibilities and future `RT.edge` ingress. |

### 6.2 Edge bootstrap

For `role=edge`, `SY.orchestrator` should:

1. Bootstrap the host over SSH like any other hive.
2. Install core binaries.
3. Write `/etc/fluxbee/hive.yaml` with `role: edge`.
4. Enable the minimal edge service profile.
5. Apply local egress NAT/firewall if `egress.enabled=true`.
6. Start `RT.gateway` and `SY.orchestrator`.
7. Verify WAN connectivity to motherbee.
8. Verify outbound internet egress from the edge host.

The minimal edge service profile should be small:

- `RT.gateway`
- `SY.orchestrator`
- `SY.config.routes`
- `SY.identity`
- `SY.opa.rules`
- Future: `RT.edge`

Edge should not run the full motherbee stack by default.

Rationale:

- `SY.config.routes` writes `/jsr-config-<hive>`, which the local router reads for routes, VPNs, and taps.
- `SY.identity` writes `/jsr-identity-<hive>`. `RT.edge` and the local router need this replicated identity view for tenant/ILK/ICH-aware ingress behavior.
- `SY.opa.rules` writes `/jsr-opa-<hive>`. This keeps policy-based target resolution available if `RT.edge` injects messages without an explicit destination.
- `SY.orchestrator` owns edge host reconciliation: service supervision, NAT/firewall reconciliation, and future edge-specific health checks.
- `RT.gateway` owns Fluxbee WAN connectivity to motherbee and other hives.

The edge profile should not include by default:

- `SY.admin` — administrative entry remains motherbee-centered; edge is controlled through motherbee and WAN.
- `SY.vault` — motherbee remains the canonical vault backend.
- `SY.storage` — edge should not persist system-wide message storage by default.
- `SY.cognition` — edge ingress should forward traffic, not run cognitive processing by default.
- `SY.policy` — not required for initial edge ingress/egress. It can be added later if edge-local policy auditing is needed.
- `SY.timer`, `SY.wf-rules`, `SY.frontdesk.gov`, `SY.architect` — not part of the edge infrastructure role.

### 6.3 Worker bootstrap

For `role=worker`, `SY.orchestrator` should:

1. Bootstrap the host over SSH like today.
2. Generate worker `hive.yaml`.
3. If motherbee has `egress.edge_ip`, inject `egress.gateway_ip`.
4. Configure or validate the default IPv4 route through that gateway.
5. Block or detect unmanaged IPv6 egress.
6. Verify outbound HTTPS through the edge.

The verification should report explicit fields:

```json
{
  "egress_configured": true,
  "egress_gateway_ip": "192.168.8.1",
  "egress_ipv4_ready": true,
  "egress_ipv6_blocked": true,
  "egress_public_ip": "203.0.113.42"
}
```

No silent success: if IPv4 works but IPv6 is still able to bypass the edge, the result should warn or fail depending on the deployment mode.

## 7. Edge NAT Rules

The edge host is the only host that performs NAT for worker internet access.

Required behavior:

1. Enable IPv4 forwarding.
2. NAT/MASQUERADE traffic from LAN CIDR to the edge WAN interface.
3. Allow forwarding from LAN to WAN.
4. Allow WAN to LAN only for `ESTABLISHED,RELATED` traffic.
5. Block IPv6 forwarding unless a later explicit IPv6 model is implemented.

The orchestrator should write owned, idempotent config. Preferred files:

| Purpose | File |
|---------|------|
| IPv4 forwarding | `/etc/sysctl.d/99-fluxbee-egress.conf` |
| Firewall/NAT rules | backend-specific file owned by Fluxbee, preferably nftables |

The first implementation should prefer `nftables` where available. UFW integration can be added later if needed, but UFW should not force global forwarding defaults such as unrestricted `DEFAULT_FORWARD_POLICY="ACCEPT"`.

### 7.1 Firewall port profile by role

The edge role has a different port profile from motherbee and worker hives.

Motherbee:

| Port | Direction | Scope | Purpose |
|------|-----------|-------|---------|
| `9000/tcp` or configured `wan.listen` | inbound | internal hives/edges only | `RT.gateway` Fluxbee WAN listener |
| `9100/tcp` or configured `identity.sync.port` | inbound | internal hives/edges only | `SY.identity` primary sync endpoint |
| `8080/tcp` | local/proxy only | localhost or admin proxy | `SY.admin` HTTP API |
| `3000/tcp` | local/proxy/internal only | admin network | `SY.architect` UI/API |
| Syncthing ports | inbound | managed hives only | blob/dist sync when enabled |

Worker:

| Port | Direction | Scope | Purpose |
|------|-----------|-------|---------|
| `22/tcp` | inbound | motherbee/admin source only | bootstrap and break-glass SSH |
| `9000/tcp` | inbound | normally closed | workers usually connect outbound to motherbee's `wan.listen` |
| `4222/tcp` | local only | localhost | embedded NATS |

Edge:

| Port | Direction | Scope | Purpose |
|------|-----------|-------|---------|
| `443/tcp` | inbound on internet-facing interface | public internet | future `RT.edge` HTTPS ingress |
| `80/tcp` | inbound on internet-facing interface | optional | only if an HTTP redirect or future ACME mode requires it |
| `22/tcp` | inbound on LAN/control interface | motherbee/admin source only | bootstrap and break-glass SSH |
| `9000/tcp` | inbound on LAN/control interface | only if edge declares `wan.listen` | `RT.gateway` listener; not public internet |
| `9100/tcp` | inbound | closed | edge identity is a replica and connects outbound to motherbee |
| `4222/tcp` | local only | localhost | embedded NATS |

The edge should not open the full motherbee port profile. It is a gateway and ingress host, not the administrative center.

### 7.2 UFW behavior for edge egress

If UFW is the active firewall backend, `SY.orchestrator` should manage edge egress with explicit rules:

1. Keep incoming traffic denied by default.
2. Keep routed traffic denied by default.
3. Allow only the declared public ingress ports on the WAN interface.
4. Allow SSH/control ports only from motherbee or an explicit admin source on the LAN/control interface.
5. Add an explicit routed allow from LAN to WAN for the internal LAN CIDR.
6. Add NAT/MASQUERADE for the internal LAN CIDR out the WAN interface.
7. Block IPv6 forwarding for this phase.

Conceptual UFW shape:

```text
ufw default deny incoming
ufw default allow outgoing
ufw default deny routed

ufw allow in on <wan_iface> to any port 443 proto tcp
# optional:
# ufw allow in on <wan_iface> to any port 80 proto tcp

ufw allow in on <lan_iface> from <motherbee_ip> to any port 22 proto tcp
# only if edge has wan.listen:
# ufw allow in on <lan_iface> from <motherbee_ip> to any port 9000 proto tcp

ufw route allow in on <lan_iface> out on <wan_iface> from <lan_cidr> to any
```

The NAT block must be inserted into UFW's before-rules or an equivalent Fluxbee-owned include:

```text
*nat
:POSTROUTING ACCEPT [0:0]
-A POSTROUTING -s <lan_cidr> -o <wan_iface> -j MASQUERADE
COMMIT
```

The implementation must use marked, idempotent blocks:

```text
# BEGIN FLUXBEE EDGE EGRESS NAT
...
# END FLUXBEE EDGE EGRESS NAT
```

Do not set broad forwarding policy such as unrestricted `DEFAULT_FORWARD_POLICY="ACCEPT"` as the main mechanism. The edge should permit only the declared LAN-to-WAN routed path and stateful return traffic.

Current implementation note:

- `SY.orchestrator` currently opens simple port rules via `ufw allow <port>/<proto>`.
- It currently opens `wan.listen` and motherbee `identity.sync.port`.
- It does not yet manage UFW routed rules, NAT before-rules, interface-specific allows, or an edge-specific port profile.

## 8. IPv6 Policy

For this phase, IPv6 is blocked for egress.

Reason: IPv4 NAT can be correctly controlled through the edge. If workers have a separate IPv6 default route, they may bypass the edge and reach the internet outside the declared egress path.

Required behavior:

- Edge must not forward IPv6 from LAN to WAN.
- Workers must not have unmanaged IPv6 default egress.
- If IPv6 cannot be blocked safely, orchestrator must report `EGRESS_IPV6_UNMANAGED`.

Future work can define a proper IPv6 egress model with firewall rules, delegated prefixes, and explicit policy. That is out of scope for the first egress NAT implementation.

---

## 9. Relationship With `RT.edge`

`RT.edge` is the future public ingress runtime described by `edge-control-protocol.md`.

It handles:

- HTTPS listener.
- TLS certificate material.
- JWT validation.
- Tenant assignment cache.
- Translation from public HTTP requests to Fluxbee L2/WAN messages.

It does not need to own generic internet egress for workers.

The edge host can run both:

- `RT.edge` for ingress.
- `SY.orchestrator`-managed OS NAT/firewall for egress.

These are separate responsibilities on the same host.

---

## 10. Relationship With NATS

NATS remains local control/data event infrastructure inside each hive.

Egress to internet does not use NATS:

- An AI node calling OpenAI opens HTTPS directly.
- The OS routes that connection through the edge as default gateway.
- The edge NATs it to the public internet.

NATS configuration should not be coupled to egress NAT.

---

## 11. Multiple Edges

Multiple edge hives are possible, but the first implementation should support only one active egress edge per motherbee deployment:

```yaml
egress:
  edge_hive: "edge-1"
  edge_ip: "192.168.8.1"
```

Future multi-edge support may add:

- Per-worker edge assignment.
- Failover edge.
- Load-balanced public ingress.
- Regional edge pools.

Those are intentionally out of scope for the first implementation.

---

## 12. Implementation Notes

Recommended incremental path:

1. Add `role=edge` support to `SY.orchestrator` hive validation.
2. Add `role=edge` support to `SY.identity` as a non-primary replica role.
3. Add `system_nodes.edge` or a built-in minimal edge profile.
4. Ensure identity system-ILK seeding reads the edge system node list, not the worker list.
5. Extend `add_hive` with optional `role`.
6. Generate edge `hive.yaml` for `role=edge`, including `identity.sync.upstream`.
7. Add egress NAT reconciliation on edge orchestrator startup.
8. Inject `egress.gateway_ip` into new workers when motherbee declares egress.
9. Add worker egress verification.
10. Add IPv6 bypass detection/blocking.
11. Document operational checks in `07-operaciones.md`.

Current implementation note:

- `SY.orchestrator` currently supports only `role=motherbee|worker`.
- `SY.identity` currently supports only `role=motherbee|worker`.
- Both need explicit `edge` handling before this profile can boot cleanly.

The first implementation should optimize for a simple, reliable single-edge deployment rather than a fully general firewall product.
