# add_hive `ssh_access=key_only_persist` — per-spoke recovery key in the vault (spec v1)

Status: **DESIGN LOCKED, NOT BUILT.** Grounded against `src/bin/sy_orchestrator.rs`
(line numbers as of commit `71cb08a`). This reverses the deliberate SO-02
"SSH-is-bootstrap-only" invariant, so it is gated behind an **off-by-default** flag and a
**verify-before-revoke** safety that makes a lock-out impossible.

## Why (user decision, 2026-07-20)

Today, after a successful `add_hive`, `revoke_bootstrap_ssh_access` unconditionally strips
motherbee's (MB) bootstrap key **and** the `/etc/sudoers.d/fluxbee-orchestrator` grant, so
MB has **no SSH path back** to a joined spoke (management is mesh-only). That is clean, but
leaves **no recovery path** if a spoke's mesh breaks, and it contradicts
`reconcile_hive_tls_material` (~1218) which already **assumes `ssh_with_key` works against
"connected" hives** — a latent bug the revoke creates.

Decision (AskUserQuestion): opt-in `ssh_access=key_only_persist` that leaves SSH open
**key-only** (password auth off) with a **per-spoke** private key stored in the vault for
recovery. Per-spoke (not the single global MB key) for blast-radius isolation + clean rotation.

## Target end-state (opt-in path)

After `add_hive {..., ssh_access:"key_only_persist"}`:
- The spoke's `authorized_keys` holds a **per-spoke** ed25519 pubkey; MB's bootstrap key is
  removed (by material).
- `PasswordAuthentication no` (hardened).
- The `/etc/sudoers.d/fluxbee-orchestrator` NOPASSWD grant is **kept** (the per-spoke key
  needs sudo to be a real recovery path).
- The per-spoke **private** key is in the vault under `ssh:<hive_id>`.
- Response: `ssh_bootstrap_revoked:true` (MB key gone), `ssh_access:"key_only"`,
  `spoke_key_vault_ref:"ssh:<hive_id>"`.

Default (`ssh_access:"revoke"`, or field absent) = **exactly today's behavior** — no change.

## Current facts (verified, `71cb08a`)

- Single shared bootstrap key `MOTHERBEE_SSH_KEY_PATH` = `/var/lib/fluxbee/ssh/motherbee.key`
  (`:59`), generated by `ensure_motherbee_ssh_key` (`:1044`), **not in the vault**.
- `revoke_bootstrap_ssh_access` (`:19577`) removes sudoers **and** greps the MB key material out
  of `authorized_keys`. It filters **by material**, so a separately-seeded per-spoke key
  (different material) SURVIVES it.
- `revoke_bootstrap_authorized_key_with_key` (`:19628`) removes **only** the MB key material
  from `authorized_keys` over the key channel — **keeps sudoers**. ← use this in the persist branch.
- `apply_add_hive_ssh_controls_after_finalize` (`:19299`) does restrict (`from=`) + harden
  (password off, `disable_remote_password_auth_with_access` + verify). Called at `:17539 / :18067 / :18798`.
- `verify_remote_key_access_after_hardening` (`:19418`) = `ssh -i <key> ... sudo -n /bin/bash -lc 'exit 0'`
  — the primitive for **verify-before-revoke** (run it with the PER-SPOKE key path).
- The orchestrator has **no in-process VaultClient**; it already writes the vault over the mesh
  via `orchestrator_admin_command` → `send_admin_rpc` (see `purge_vault_secrets_for_ilk`
  `:14818`, `orchestrator_admin_command` `:14991`). `vault_put` is the identical call.
- Vault write schema (`sy_admin.rs`): `{key, value, metadata:{resource_type, tenant_id, owner_node}}`.
  Root tenant const `fluxbee_sdk::DEFAULT_ROOT_TENANT_ID` (`crates/fluxbee_sdk/src/identity.rs:756`).
  `resource_type:"ssh"` is an accepted Custom type (`vault.rs` normalize).
- The three flows are structurally identical: `add_hive_flow` (`:16390`),
  `add_egress_hive_flow` (`:17535`), `add_ingress_hive_flow` (`:18087`). Factor the new logic
  into helpers to avoid triplication.

## Implementation plan

1. `resolve_add_hive_ssh_access(payload) -> SshAccess` near `resolve_add_hive_harden_ssh`
   (`:18988`). Default `Revoke`; `"key_only_persist"` → `KeyOnlyPersist`. (Bool alias
   `persist_spoke_key` optional.)
2. `generate_spoke_ssh_keypair() -> Result<(priv_pem, pub_openssh)>` near `:1085` — `ssh-keygen
   -t ed25519 -N ''` into a `0700` tempdir, read both, delete the dir.
3. `vault_put_spoke_ssh_key(state, hive_id, priv_pem)` near `purge_vault_secrets_for_ilk`, with
   the same `cfg(test)`/`cfg(not(test))` split so unit tests never hit the mesh. Real impl:
   `orchestrator_admin_command(action="vault_put", target=Some(PRIMARY_HIVE_ID),
   params={key:"ssh:<hive_id>", value:{private_key:priv_pem}, metadata:{resource_type:"ssh",
   tenant_id:DEFAULT_ROOT_TENANT_ID, description:...}})` — a POOL secret (NO owner_node) so the
   admin/operator can retrieve it; owner_node=SY.orchestrator scopes it orchestrator-ILK-only
   (even admin gets UNAUTHORIZED). Key MUST be `ssh:<hive_id>` (colon) — validate_key rejects `/`.
   **NEVER `tracing` the params** (private key).
4. New helper `finalize_spoke_key_persist(address, mb_key_path, mb_pub, user, hive_id, state)`
   used by all three flows, invoked **in place of** the plain controls+revoke when the flag is
   set. Ordering (the safety spine):
   a. `generate_spoke_ssh_keypair()`; write the priv to a `0600` temp path.
   b. Seed the per-spoke **pubkey** into `authorized_keys` over MB's key access (append; reuse
      the append path used by `apply_remote_from_only_authorized_key_with_access`, or a small
      key-channel append helper).
   c. Force harden: `disable_remote_password_auth_with_access` + `verify_remote_ssh_hardening_with_access`.
   d. **VERIFY-BEFORE-REVOKE**: `verify_remote_key_access_after_hardening(address, <per-spoke
      temp key path>, user)` — confirm the PER-SPOKE key logs in AND `sudo -n` works. If this
      fails → **do NOT revoke**; keep MB's key, return `ssh_access:"degraded_kept_bootstrap"` +
      an error note. This makes lock-out impossible.
   e. `vault_put_spoke_ssh_key(...)` — fail-soft: on error, still keep the working per-spoke key,
      return `spoke_key_vault_ref:null` + a warning (the key works; it's just not backed up).
   f. `revoke_bootstrap_authorized_key_with_key(address, mb_key_path, user, mb_pub)` — removes
      **only** MB's key, **keeps sudoers** and the per-spoke key.
   g. Delete the temp priv key file.
5. Guard the three existing `apply_add_hive_ssh_controls_after_finalize` + `revoke_bootstrap_ssh_access`
   call sites: `if ssh_access == KeyOnlyPersist { finalize_spoke_key_persist(...) } else { <today> }`.
6. Response fields in all three flows: `ssh_access`, `spoke_key_vault_ref`, keep `ssh_bootstrap_revoked`.

## Open sub-decisions (confirm before build)

- **owner_node scoping**: RESOLVED — omit owner_node (root-tenant POOL secret, like
  `storage_postgres_url`). Lab-verified that owner_node=SY.orchestrator makes the secret
  orchestrator-ILK-only (admin/operator read = UNAUTHORIZED), which defeats recovery; a pool
  secret is readable by SY system callers + the admin, so an operator can break-glass it.
- **DONE (commit e58d21a)**: `reconcile_hive_tls_material` now reads `ssh:<hive_id>` from the
  vault for a key_only_persist hive (falls back to `motherbee.key` for revoke/legacy hives),
  closing the reconcile↔revoke contradiction. Lab-verified: MB reconcile logs "reaching
  key_only_persist hive via its per-spoke recovery key" for the persist hive and reaches it.
- **Blast radius**: a vault compromise now yields sudo-capable shell on every persist-spoke. This
  is the accepted cost of a recovery path; document it in the security model.

## Lab validation plan (before declaring done)

Fresh `add_hive {ssh_access:"key_only_persist"}` on a clean VM, then assert on the box:
`sshd -T | grep passwordauthentication` = `no`; `authorized_keys` has the per-spoke key and
**not** MB's material; the sudoers grant is present; `ssh -i <vault-retrieved key> fluxbee@spoke
sudo -n true` succeeds; MB's `motherbee.key` does **not** authenticate. Then
`GET /hives/<hive>/vault/secrets/ssh:<hive_id>` (admin) returns the key. Negative: force the
verify (step d) to fail → assert the join keeps MB's key and reports `degraded_kept_bootstrap`
(no lock-out).
