# SY.edge / INGRESS audit - add_ingress, externalize and IO.cloud

Date: 2026-07-06  
Repository: this one (`fluxbee`)  
Branch audited: `daily_onworking_coa`  
Commit audited: `3fa9646`  
Focus: `docs/edge-ingress-spec-v6.md`, `src/bin/sy_edge.rs`, `src/bin/sy_admin.rs`, `src/bin/sy_orchestrator.rs`, router/policy, vault, identity, packaging and `nodes/io/io-cloud`.

## Executive summary

The INGRESS mechanism already has important pieces implemented: `SY.edge` exists, is packaged, can bind an HTTP/HTTPS frontend, persists routes by `ich`, rehydrates secrets from vault by `secret_ref`, forwards to `owner_l2_name`, and `SY.admin` implements `externalize`/`unexternalize` with ICH ownership validation. `add_ingress` also recognizes the `ingress` role, copies core binaries and renders the remote configuration.

However, the system is not yet ready for safe public exposure. The main problem is not in the basic HTTP path, but at the authority and provisioning boundaries:

1. **Critical:** `SY.edge` accepts `EDGE_OPEN_URL` and `EDGE_CLOSE_URL` without validating who sends the command, and the router does not protect those actions.
2. **High:** `add_ingress` generates units for `SY.edge` but does not enable/start it, so it can report success without a public listener.
3. **High:** the unit generated by `add_ingress` does not wait for `rt-gateway`/`SY.vault`, unlike the packaging.
4. **High:** TLS is optional in `add_ingress`, although the spec requires `tls_vault_key` for HTTPS ingress.
5. **High/Medium:** the network scope of `SY.edge` is still too broad because of the router's general rule for system nodes.

The operational conclusion is that the "spine" exists, but authority, startup and reachability still have to be closed before the `add_ingress -> externalize -> internet -> internal IO` circuit can be considered complete.

## Findings

### EDGE-2026-07-06-01 - Critical - `SY.edge` accepts opening/closing URLs without validating authority

Status: Mitigated and validated in the lab

Evidence:

- The `SY.edge` loop processes `MSG_EDGE_OPEN_URL` and `MSG_EDGE_CLOSE_URL` directly, before other system actions (`src/bin/sy_edge.rs:296-335`).
- `apply_open_url` parses the payload as `EndpointRow`, resolves the secret, inserts into the registry, persists and replies, but does not validate `req.routing.src_l2_name`, `req.routing.src`, the hive or the caller's authority (`src/bin/sy_edge.rs:375-405`).
- `apply_close_url` removes the entry by `ich` and persists without validating the origin (`src/bin/sy_edge.rs:420-455`).
- The `PROTECTED_SYSTEM_ACTIONS` table does not include `EDGE_OPEN_URL` or `EDGE_CLOSE_URL` (`src/router/system_policy.rs:25-44`).
- The router allows VPN traffic if `src` or `dst` is a system node (`src/router/mod.rs:5198-5211`), and `SY.edge` qualifies as a system node by its `SY.` prefix (`src/router/mod.rs:5183-5185`).
- The spec says that publishing an endpoint must go through `SY.admin`/authority, and that `EDGE_OPEN_URL` is a service command issued to the edge after ownership is resolved (`docs/edge-ingress-spec-v6.md:122-189`).

Impact:

An internal node that can route to `SY.edge` can publish or close arbitrary public routes. In the worst case it can register its own `ich` or someone else's, choose `owner_l2_name`, set `auth_mode = "public"` and expose a handler without going through `SY.admin` authorization. It can also cause a logical DoS by closing existing routes.

Recommendation:

- Add `MSG_EDGE_OPEN_URL` and `MSG_EDGE_CLOSE_URL` to a protected router policy, with explicit allowed origins.
- Add a local defense in `SY.edge`: reject mutating commands if `src_l2_name` does not match an expected authority.
- Define the exact authority: probably `SY.admin@motherbee` for the externalize of IO owners and, only if needed, `SY.orchestrator@<ingress_hive>` for internal provisioning operations.
- Validate payload invariants in the edge even when the caller is authorized: `owner_l2_name` must be `IO.*`, `ich` non-empty, `auth_mode` supported, `inbound_family` not system/protected.
- Add negative tests that invoke `EDGE_OPEN_URL` from an unauthorized `IO.*` and from a disallowed `SY.*`.

### EDGE-2026-07-06-02 - High - `add_ingress` does not enable or start `sy-edge`

Status: Mitigated and validated in the lab

Evidence:

- `add_ingress_hive_flow` resolves the ingress-role system nodes and generates units for those nodes (`src/bin/sy_orchestrator.rs:17827-17849`).
- The loop that enables/restarts remote services only includes `rt-gateway` and `sy-orchestrator` (`src/bin/sy_orchestrator.rs:17858-17874`).
- The wait that follows only checks the remote `sy-orchestrator` (`src/bin/sy_orchestrator.rs:17875-17890`).
- `name_to_service` maps `SY.edge` to `sy-edge`, so there is a local way to derive the expected service (`src/bin/sy_orchestrator.rs:3794-3803`).
- The `add_ingress` spec takes it as given that the ingress worker installs/runs `SY.edge` as part of the circuit (`docs/edge-ingress-spec-v6.md:344-364`).

Impact:

`add_ingress` can finish successfully with WAN/orchestrator connected, but without `SY.edge` running and without a public listener. That breaks the basic criterion of "routing the internet to internal nodes" and creates a false-positive state that is hard to operate.

Recommendation:

- In `add_ingress`, enable and start all the required `ingress_system_nodes`, at least `SY.config.routes` and `SY.edge`.
- Add a specific health gate for `sy-edge`: systemd active, connection to the router and, if `edge.listen` is configured, an active bind/listener.
- Include `SY.edge` in the final `add_ingress` response with flags such as `edge_service_active`, `edge_frontend_bound`, `edge_tls_loaded`.
- Add a render/provisioning test that fails if `SY.edge` is left out of the list of enable/start services.

### EDGE-2026-07-06-03 - High - Unit generated by `add_ingress` does not wait for router/vault

Status: Mitigated and validated in the lab

Evidence:

- The generic unit that `add_ingress` writes for non-orchestrator nodes only declares `After=network.target` (`src/bin/sy_orchestrator.rs:17839-17844`).
- The unit installed by `scripts/install.sh` for `sy-edge` must wait for the local `rt-gateway.service`, but not for a local `sy-vault.service`: in an ingress hive the vault lives on the motherbee and is reached over the mesh.
- The `.deb` package unit must keep the same semantics (`packaging/build-deb.sh`, `scripts/install.sh`).
- `SY.edge` loads TLS from vault at startup if `tls_vault_key` or cert/key are configured (`src/bin/sy_edge.rs:241-245`).
- If TLS was requested and could not be loaded, `SY.edge` refuses to bind plaintext and continues without a public frontend (`src/bin/sy_edge.rs:276-287`).

Impact:

On a freshly provisioned ingress host, `SY.edge` can start before the router/vault. If the vault does not answer during the initial TLS load, the process stays alive but without a listener. Since it neither exits with an error nor keeps retrying TLS, systemd does not repair it automatically.

Recommendation:

- Reuse for `add_ingress` the same unit template that packaging uses for `sy-edge`.
- Declare `After=`/`Wants=` for `rt-gateway.service`; do not depend on a local `sy-vault.service` on ingress.
- If TLS was requested and loading it from `SY.vault@motherbee` fails, exit non-zero so that systemd restarts it, or implement retry/backoff of the TLS fetch before binding.
- Add a test that compares the unit generated by `add_ingress` with the minimum dependency requirements of `sy-edge`.

### EDGE-2026-07-06-04 - High - TLS is optional for a public ingress

Status: Mitigated and validated in the lab

Evidence:

- `resolve_add_hive_ingress_section` requires `ingress.listen`, but `tls_vault_key` is optional (`src/bin/sy_orchestrator.rs:204-245`).
- `add_ingress_hive_flow` omits the `edge.tls` block entirely when there is no `tls_vault_key` (`src/bin/sy_orchestrator.rs:17760-17770`).
- `SY.edge` decides from config/env whether TLS was requested; if it was not requested, it brings up a plaintext frontend (`src/bin/sy_edge.rs:241-245`, `src/bin/sy_edge.rs:913-915`).
- The spec marks `tls_vault_key` as a condition for HTTPS ingress and documents that its absence implies plaintext only as a technical behavior (`docs/edge-ingress-spec-v6.md:356-360`).

Impact:

An `add_ingress` can leave a public HTTP service without TLS, even if the configured port is 443 or the operator assumed HTTPS. For an edge exposed to the internet, this degrades confidentiality, authenticity and client compatibility.

Recommendation:

- Require `ingress.tls_vault_key` for `role=ingress` by default.
- Allow plaintext only with an explicit development opt-in, for example `ingress.allow_plaintext = true`, ideally rejected if `listen` uses port 443.
- Reflect the final mode in the `add_ingress` response.
- Add config tests: `ingress.listen` without TLS must fail unless there is an explicit opt-in.

### EDGE-2026-07-06-05 - High/Medium - `SY.edge` keeps overly broad internal reachability

Status: Mitigated within the alpha scope and validated in the lab

Evidence:

- The spec says that the scope of `SY.edge` must be limited to IO handler nodes and that it must not have blanket reachability as a system node (`docs/edge-ingress-spec-v6.md:106-118`).
- The alpha scope still lists narrowing the edge's reachability scope as pending (`docs/edge-ingress-spec-v6.md:376-392`).
- `add_ingress` writes an empty `sy-config-routes.yaml` on the ingress host (`src/bin/sy_orchestrator.rs:17797-17808`), with no specific allowlist for handlers.
- The router allows routes between hives if `src` or `dst` is a system node (`src/router/mod.rs:5198-5211`).
- `SY.edge` forwards HTTP requests by building messages to `owner_l2_name` according to the registry (`src/bin/sy_edge.rs:1064-1234`), but the router does not limit the process to those destinations.

Impact:

Even though the edge registry forwards only to the configured owner, the `SY.edge` process still has system-node privilege at the routing level. If the process is compromised because it is exposed to the internet, it can try to send internal messages to more nodes than the spec allows.

Recommendation:

- Take `SY.edge` out of the general system-node reachability exception, or add an explicit negative exception for the edge.
- Introduce a router policy specific to `SY.edge`: only data messages to `owner_l2_name`/families authorized by the registry, and only control commands from an approved authority.
- Consider never allowing `SY.edge` to send protected `SYSTEM`, except for strictly defined local status/config.
- Add router tests: `SY.edge -> SY.identity`, `SY.edge -> IO.not-externalized` and `IO.* -> SY.edge EDGE_OPEN_URL` must be rejected.

### EDGE-2026-07-06-06 - Medium - `externalize` ignores the ICH `enabled` flag

Status: Mitigated and validated in the lab

Evidence:

- `ILK_ADD_CHANNEL` creates channels with `enabled: false` by default (`src/bin/sy_identity.rs:984-1080`).
- `ensure_own_ich` in IO common returns the `enabled` state, but does not enable the channel (`nodes/io/common/src/provision.rs:150-235`).
- `IO.cloud` can call `externalize` immediately after ensuring its channel if `IO_CLOUD_EDGE_NODE` is configured (`nodes/io/io-cloud/src/main.rs:114-174`).
- `SY.admin` resolves the ICH owner, but does not check that the channel is enabled before issuing `EDGE_OPEN_URL` (`src/bin/sy_admin.rs:3495-3514`).
- `IdentityIchOption` exposes the `enabled` field, and `build_ich_options` computes it (`crates/fluxbee_sdk/src/identity.rs:133-142`, `src/bin/sy_identity.rs:1391-1411`).

Impact:

A channel that was created but not enabled can end up published on the internet. This contradicts the "safe default" model expected for channels and can expose IO surfaces before operational approval is complete.

Recommendation:

- In `SY.admin externalize`, require that the ICH exists and that `enabled == true`, unless there is an explicit administrative flag.
- Make `IO.cloud` request that the ICH be enabled through the canonical flow before externalizing, if those are the desired semantics.
- Add tests: a disabled ICH cannot externalize; an enabled ICH can.

### EDGE-2026-07-06-07 - Medium - `list_externalized` is in the spec scope but does not exist

Status: Mitigated and validated in the lab

Evidence:

- The spec includes `list_externalized` in the command shape and in the alpha scope (`docs/edge-ingress-spec-v6.md:151`, `docs/edge-ingress-spec-v6.md:379`).
- The admin action allowlist only includes `externalize` and `unexternalize` for this area (`src/bin/sy_admin.rs:90-104`).
- `dispatch_internal_admin_command` only dispatches `externalize` and `unexternalize` (`src/bin/sy_admin.rs:3777-3784`).
- `SY.edge` has a persisted registry, but does not expose a safe action to list externalized routes (`src/bin/sy_edge.rs:713-827`).

Impact:

There is no authoritative view to reconcile what is published, audit ownership, detect drift or rebuild state after a reimage. Operating `externalize`/`unexternalize` without `list` leaves the control plane incomplete.

Recommendation:

- Implement `list_externalized` in `SY.admin` as an authorized view.
- Define whether the source of truth for listing is identity/core, the edge registry, or both with reconciliation.
- Do not expose secrets; return `secret_ref`, `auth_mode`, `methods`, `edge_node`, `ich`, `owner_l2_name`, timestamps and the sync state if there is one.
- Add authorization tests: an IO sees only its own ICHs; an internal authority sees all of them according to scope.

### EDGE-2026-07-06-08 - Medium/Low - `ingress.endpoints_json` allows a legacy/unvalidated seed

Status: Mitigated and validated in the lab

Evidence:

- `IngressSection` still has stale comments about an old shape with `{hash, ilk, handler_node}` and `NODE_CONFIG_SET` (`src/bin/sy_orchestrator.rs:180-202`).
- `add_ingress_hive_flow` accepts an optional `ingress.endpoints_json` and writes it directly as `/etc/fluxbee/edge.endpoints.json`; if it does not exist, it writes `{"endpoints":[]}` (`src/bin/sy_orchestrator.rs:17810-17825`).
- `SY.edge` expects rows with `ich`, `owner_l2_name`, `inbound_family`, `auth_mode`, `secret_ref`, etc. (`src/bin/sy_edge.rs:713-738`).
- If the file is missing or does not parse, `SY.edge` starts with an empty registry (`src/bin/sy_edge.rs:788-810`).
- The v6 spec steers the model toward an edge that is born empty, with changes made through `EDGE_OPEN_URL`/`EDGE_CLOSE_URL` commands, not through a manual endpoint seed (`docs/edge-ingress-spec-v6.md:122-189`).

Impact:

A malformed seed can produce silent 404s, drift from the source of truth, or pre-published routes that did not go through the authority flow. The risk is lower if `hive.yaml` is operator-owned, but it contradicts the control plane model.

Recommendation:

- Remove `ingress.endpoints_json` from the normal `add_ingress` contract, or limit it to a dev/migration mode.
- If it is kept, validate it against `EndpointRow` before writing it remotely.
- Update comments and docs to remove the legacy shape.
- Add a test with a legacy payload to confirm an explicit rejection.

### EDGE-2026-07-06-09 - Low/Medium - Fluxbee Cloud provisioning incomplete

Status: Closed for alpha provisioning; conversational product and specific runtimes pending

Evidence:

- The component is called `IO.cloud`; `SY.edge` is the public boundary and there is no `sy.cloud` node.
- `IO.cloud` registers/enables its ICH and externalizes with a shared bearer, fail-closed if the
  secret is missing.
- The handler implements the `create_tenant`, `put_token` and `provision_node` operations, with an
  allowlist, a canonical tenant and correlation by `request_id`.
- The caller is authenticated as Cloud-as-a-service. End-user identity is deferred by an explicit
  decision of the alpha contract.

Impact:

Fluxbee Cloud can already create tenants, store tokens and launch nodes through the ingress endpoint.
There is not yet a composite transaction with rollback, an `io.wapp` runtime, or conversational
dispatch/outbound client to the Cloud backend. End-user identity bound to the tenant is also still
missing before production.

Recommendation:

- Keep the E2E probe of the three operations as a release smoke test of the Linux package.
- Implement and publish each product runtime before requesting it with `provision_node`.
- Add end-user identity and a composite transaction only when the product contract requires it; do not
  extend the alpha bearer to general admin actions.

## Suggested remediation order

1. Lock down the authority for `EDGE_OPEN_URL`/`EDGE_CLOSE_URL` in the router and in `SY.edge`. It is the most direct risk of unauthorized publication.
2. Fix `add_ingress` so that it enables/starts `SY.edge` and health-gates the listener/TLS before reporting success.
3. Align the remote `sy-edge` unit with packaging and settle the behavior on a TLS/vault failure.
4. Make TLS mandatory by default for a public ingress, with an explicit opt-in for dev plaintext.
5. Reduce the reachability of `SY.edge` to externalized IO handlers and allowed families.
6. Enforce `ICH.enabled` in `externalize`.
7. Implement `list_externalized` and retire/validate `ingress.endpoints_json`.
