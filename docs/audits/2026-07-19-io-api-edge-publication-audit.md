# Audit and E2E closure of IO.api on SY.edge

Date: 2026-07-19

Repository: this one (`fluxbee`)

Branch: `daily_onworking_coa`

Base reviewed: `cd2ab140c1c5735ecf0898a5f6a28570c90d40bb`

Status: implementation finished and validated on Linux/Proxmox, with a documented Edge topology
limitation and a pending operational upgrade problem.

## Decision applied

`IO.api` stops being a private HTTP server and moves to the current Edge-native model:

```text
Internet HTTPS
  -> SY.edge POST /e/<ich>
  -> io.api.inbound.v1 message through the Fluxbee router
  -> instantiated IO.api
  -> fixed internal destination configured by Admin
```

No reverse proxy and no `/api/<ich>` surface were added. The publication authority is still
`SY.admin`; the public bearer is generated by Admin, and Edge is the only HTTP frontier.

Each `IO.api` instance:

- has its ILK and tenant injected by Orchestrator;
- registers its own `api_channel_id` and gets a distinct ICH;
- accepts only `POST /` and `io.api.inbound.v1` messages for its own ICH;
- validates that the router-stamped origin is the configured `SY.edge`;
- uses a fixed `io.dst_node` that the request cannot replace;
- resolves subject ILKs with an exact tenant match;
- does not listen on TCP/HTTP, and receives no secrets, API keys or Vault references in its config;
- keeps its config, ICH and publication desired state across restarts;
- supports `CONFIG_GET` and `CONFIG_SET` over the control plane.

The legacy code for the Axum listener, its own API keys, multipart/attachments and webhooks was
removed. The specs and runbooks that described that obsolete contract were removed too. The active
specification is `docs/io/io-api-node-spec.md`.

## Runtime integration

`io.api` becomes a first-class instantiable runtime, not a singleton:

- included in the Debian package and in `dist/runtimes`;
- published by the runtimes manifest;
- materialized by Syncthing on the hives;
- spawned and managed by `SY.orchestrator`;
- operable from the `SY.admin` actions/help and from the documentation that Archi consumes;
- deployable with `scripts/deploy-io-api.sh`.

The deploy helper publishes the runtime, syncs/updates the hive, creates or updates an
instance, applies typed config and waits for the publication status. A new bearer is printed only
once and is not written to the log.

## Defects found and fixed during the E2E

### 1. Authority for cross-hive distribution

The runtime publication reached Admin, but the Router and Orchestrator's defense-in-depth
validation rejected cross-hive `SYSTEM_UPDATE`/`SYSTEM_SYNC_HINT`. Those actions were added to the
special set authorized for Admin/Orchestrator in:

- `policy/system.rego` and its regenerated `policy/system.wasm`;
- `src/router/system_policy.rs`.

The authority of IO nodes and of a worker-local Admin was not widened.

### 2. Ownership of the synced tree

The package left `/var/lib/fluxbee/dist` owned by root while Syncthing runs as
`fluxbee`, which caused `permission denied`. The ownership of `dist`, `syncthing` and `blob` was aligned in:

- `packaging/deb-postinst`;
- `scripts/install.sh`;
- `SY.orchestrator`'s reconciliation when dist sync is enabled.

The first version of the reconciliation tried to apply the recursive directory helper to the
Syncthing vendor file and produced `File exists (os error 17)` at bootstrap. The file chown
was split from the recursive chown of `dist`. The final package confirmed on the three hives:

- no bootstrap error;
- Syncthing vendor with `fluxbee:fluxbee` ownership;
- runtime synced, materialized and executable on worker1;
- Syncthing `idle`, with 0 errors, 0 pull errors and 0 pending items;
- identical hashes of the manifest, the IO.api binary and Orchestrator between motherbee and worker1.

### 3. Teardown of instances on a worker

The remote teardown tried to use `SY.admin@worker1`, which does not exist because Admin is a
motherbee singleton. The Identity and Vault cleanup now targets `SY.admin@motherbee`. The unit test and
the real E2E confirm the target and the full removal.

### 4. Frontdesk handoff and RPC contract

The first `explicit_subject by_data` test after the upgrade returned
`invalid_frontdesk_response`. The payload was not corrupt: `SY.frontdesk.gov` had restarted
without an effective config and answered with its canonical error `type=error/node_not_configured`.

The circuit was closed as follows:

- Frontdesk was configured through its canonical `CONFIG_SET` and persisted the state; a later
  reinstall and restart restored it to `CONFIGURED`;
- IO.api recognizes the `type=error` payload before parsing the envelope and exposes it as
  `frontdesk_unavailable`, with the original code in the detail;
- the RPC matcher no longer accepts any correlated message: only `msg_type=user` is a success, and
  `SYSTEM/UNREACHABLE` or `SYSTEM/TTL_EXCEEDED` are terminal errors;
- the intermediate Frontdesk is configurable through `node.frontdesk_target` /
  `IO_API_FRONTDESK_TARGET`, and by default it points to the `SY.frontdesk.gov@motherbee` singleton, also
  when IO.api runs on a worker.

The final E2E tested a new subject, full registration through Frontdesk, continuation to the fixed
destination, and a second request that reused exactly the same ILK. The restart of the whole package confirmed
that Frontdesk keeps its effective config.

## Residuals

### EDGE-H4: single-hop WAN routing

`ingress1` is directly adjacent to motherbee, not to worker1. The current WAN LSA
implementation in Edge resolves a single hop, as `docs/edge-ingress-spec-v6.md` (H4) already documents.

Consequence: a publication whose `IO.api` lives on worker1 can be created, but the request from
Edge ends in HTTP 502 `HANDLER_UNREACHABLE`. The same circuit on motherbee works fully.
Solving it needs a design decision on multihop routing or on the ingress topology; that model was not
changed within this revamp.

### Package upgrade: timeout when stopping Orchestrator

On worker1 and ingress1, `apt` waited the 90 seconds of `TimeoutStopUSec`, and systemd ended the
Orchestrator with SIGKILL before the upgrade completed. The package then installed, and
Router/Orchestrator started correctly. It is a unit-lifecycle problem during
upgrade, not an IO.api one, and it is left pending for a dedicated fix.

## Conclusion

`IO.api` is ready as an instantiable Edge-native runtime, and its full circuit is validated on
motherbee. Identity, isolation between instances, bearer, configuration, restart, rotation,
unpublish and teardown were tested in the lab.

Publishing an instance hosted on a worker requires solving EDGE-H4 first. Until then,
the working location for public endpoints is a hive directly reachable by the ingress,
like motherbee in the tested topology.
